# Changelog

## Unreleased

- `jskit test` and the browser test servers run with `APP_ENV=test`, whatever the shell says, and refuse to run where `APP_ENV` is staging or production: `jskit test runs tests with APP_ENV=test, and APP_ENV is staging here: tests never run on a staging or production server. Run them where APP_ENV is unset, development or test.` The Nix launcher still sets only `NODE_ENV=production` by default, never `APP_ENV`.
- A packaged app's `<name> --migrate` starts an app that has no `db:migrate` script, saying there is nothing to migrate, where it exited 1 (`<name> has no db:migrate script.`). A host that runs every app's service with `--migrate` restarted such an app forever and its check never got an answer. `<name>-migrate` still refuses an app without the script. `<name>-prepare` also makes each folder its settings name for the app's files with an absolute path (`JSKIT_STORAGE_FS_BASE_PATH`, `AUTH_LOCAL_STORE_DIR`, `AUTH_OIDC_STORE_DIR`), mode 0700, owned by `--user`. A host's data folder belongs to root until its start step hands it over, so the app's service could not write there.
- `jskit check` refuses an app whose own `json-rest-api` declaration differs from the version JSKIT's packages require (`resource-runtime` and `crud-core` require it exactly), and a lockfile that installs `json-rest-api` more than once, with the fix: `Pin json-rest-api to <version>`. Beside a second copy, every write the app's `api.transaction` reaches inside JSKIT failed with `RestApiWriteError: transaction must be an active transaction from api.transaction` (an app pinning 3.1.9 under JSKIT 0.2.80, which requires 3.1.10), and neither command noticed. `jskit update` moves such a direct pin to the catalog's version with the JSKIT packages. The check applies only when one of the app's JSKIT packages needs `json-rest-api`, directly or through another JSKIT package.
- New `jskit package nix` writes `package.nix`, the app as one Nix package that builds with no network access, for a host that runs apps only as Nix packages. The file is the same for every app: it reads `package.json` and `package-lock.json` while Nix evaluates it and fetches each npm download by the integrity hash the lock gives it, so a changed lock needs no change to it and there is no hash to keep up to date. The build installs the lock offline (`npm ci` from a cache of exactly those files), runs the install scripts (`npm rebuild`; node-gyp compiles a native addon against the package's Node.js, its major version from `engines.node`), runs `npm run build`, and keeps the app with its production dependencies. The package's `bin/` holds `<name>` (the start script as `npm start` runs it, `NODE_ENV=production` by default, `--migrate` running `db:migrate` first), `<name>-migrate`, `<name>-check` (waits for `GET /api/health` to answer 200) and `<name>-prepare` (writes a settings JSON as a 0600 env file for the service's user); each takes `--env FILE`. The command refuses, writing nothing, an app whose lock holds a git, `file:` or hashless dependency or a link outside the app, one with no `start` script or no lock, and a `package.nix` it did not write. Plain `jskit check` checks a `package.nix` the command wrote: `package/nix-current` (the installed JSKIT writes another: run the command again), `package/nix-manifest` and `package/nix-offline`. The guide's [Package an App with Nix](/guide/app-setup/package-with-nix) describes it.
- `jskit update` approves `@jskit-ai/material-web`'s install script, which patches Vuetify's idle loaders (vuetifyjs/vuetify#23393), in the root `package.json`'s `allowScripts` (`"@jskit-ai/material-web": true`) when the app or one of its workspaces declares the package, so npm runs it without its unreviewed-script warning and a strict install (`strict-allow-scripts`) accepts it. An entry that denies it (`false`, for the name or one version) stays.
- `nav/missing-parent` and `nav/top-level-parent` read a dynamic page that serves literal main-navigation destinations as top-level: `modules/[moduleKey]/index.vue` serves the placements `/modules/incidents` and `/modules/hazards`, so it needs no parent and declares none. A literal destination matches a page's route segment by segment, each `:param` standing for exactly one non-empty segment; the page's deeper pages (`/modules/:moduleKey/settings`) are still inner pages. The same holds for package routes, by suffix or by a link's `to`. Before, only an exact match counted, so such a page was reported as missing a parent, and declaring one gave a main-navigation page an Up arrow.
- `jskit check`'s data part skips a directory the app's ESLint config ignores when that directory holds an ESLint config of its own, as `eslint .` does: ESLint enters a directory only when the config of the directory above does not ignore it, so a nested config never brings back what a parent config ignores. The check asked each file's nearest config alone, so an ignored git submodule or vendored application with its own `eslint.config.mjs` was read as the app's source, and its infrastructure exceptions failed the app's baseline (`data/baseline`). Server code in such a directory, told from the directory of the config that ignores it, is still read and fails `data/lint-config`; a nested config that no config above ignores is read as before, and alone judges what its directory holds. `jskit test --databases` reads the same files for table resources.
- **Breaking.** `jskit/narrow-in-query` (in `typedFeaturesConfig`) reports code that narrows the rows a read answered instead of asking the store for them: `.filter()`, `.find()`, `.some()`, `.every()`, `.slice()`, a lone `.length`, or a loop that skips rows with `continue`, over the rows of an awaited `query()`, `queryAll()`, `queryPages()`, json-rest-api `api.resources.<name>.query()` or Knex builder in the same function (held, destructured from `records` or `data`, or used at once). A section picker that read the newest 200 sections of every module and kept one module's in code answered wrong once the table outgrew the page. Its message says whether the read was every row, a page (wrong as the table grows) or a `query()` with no page size (a default-capped page). Mapping, grouping and code that needs every row it read pass: rows also handed on whole (returned, passed, stored, mapped or walked in full) with a subset derived beside them, rows matched against other items in a loop or a callback (an in-memory join, one read instead of one per item), any use of a read of at most one row (its page size or `take` is read also through a wrapper call the params pass through, `query(forViewer({ page: { size: 1 } }))`, and after a spread), and the `.slice()` of a read that asks for one row more than it keeps (`limit(size + 1)`, `take: size + 1`) to learn whether more follow. Code that needs every row says so: `// readable-check: allow narrow-in-query - every row: <why>` above the read or the narrowing, a new reason prefix. Upgrading: put the filter, limit, existence check or count in the read (a searchSchema filter, `take`, a page of size 1, `aggregate()`).
- **Breaking.** `jskit/search-on-server` (in `clientFeaturesConfig`) reports a search over a list's loaded page: a `computed()` that filters a list composable's items (`useList`, `useCrudList`, `useCrudListScreen` and the rest) by a search ref (a ref named with the word search, query, term or keyword, or `q`; not `activeTerminal`), and a `v-autocomplete` (or a `searchable` `SelectField`) over a list's items or `resolveLookupItems(...)` without `no-filter` or an `update:search` handler. Such a search misses every row past the loaded page. Upgrading: turn on the list's search, which sends `q`, or add `no-filter` and `@update:search` (a lookup's `setLookupSearch`).
- **Breaking.** `jskit check` fails a lookup field (`lookup: "<namespace>"` or a relation `{ kind: "lookup", namespace }`) or a CRUD list screen (`useCrudListScreen({ resource })`, in a `.js` file or a Vue component's script) whose app table resource defines no `searchSchema.q`, on the resource or its owns entry (`data/search-q`): the picker and the list's Search box send what the person types as `q`, which such a resource refuses. Upgrading: give the resource `searchSchema: { q: { type: "string", oneOf: [...], filterOperator: "like" } }`.
- **Breaking.** Plain `jskit check` compares each application package's manifest with its features (`manifest/capabilities`): for every root or workspace `package.json` that declares server providers (`jskit.runtime.server.providers`), it loads them through the kernel the package resolves (`packageCapabilityDrift` of `@jskit-ai/kernel/server/platform`) and fails a capability they provide that `jskit.capabilities.provides` does not list, one the manifest provides that none of them does, and one they require that `jskit.capabilities.requires` does not list (the kernel's own and the package's own aside, optional ones never), each at its line of the manifest, and a package whose providers do not load. The server refused such a manifest only at start-up. A manifest requirement no feature has is listed for review, as only install time may need it (the database a migration needs). Upgrading: run `npx jskit check` and add or remove each capability it names (the typed-features guide's Package manifest).
- **Breaking.** New lint rule `jskit/selection-field`, an error in `clientFeaturesConfig` as the other client rules are, so an app that lists its client code there may get new findings: a `v-select`, `v-autocomplete` or `v-combobox` (or `VSelect`, `VAutocomplete`, `VCombobox`) whose `:items` are not fixed, and a `SelectField` whose items are not fixed that binds no `loading`. Fixed items are a list written out in the template, an identifier (or a member of one) bound to a top-level `const` that holds a list or object written out, as is, frozen (`Object.freeze`, `deepFreeze`) or Vue's `computed()` over a list written out, or an import from a `shared` module; a v-for or slot variable of the same name is not one. A static `items` attribute and a selection with no items at all (a combobox taking typed entries) load nothing and pass, and a `SelectField` with a `v-bind` object may get `loading` through it. The rule never guesses from the model's name. A selection whose options are in memory and whose value is no record id says why above the element: `<!-- readable-check: allow selection-field - data: <where the options come from> -->`. To fix a finding, render options that load from the server, or a value that is a record id, with `SelectField` from `@jskit-ai/http-web/client/components/SelectField` and bind `:loading` while they load (the client guide's Selection fields).
- `jskit/no-duplicate-helper` leaves alone a component's small closure over its own state: a function of at most two statements in `<script setup>` whose every name from outside itself is a binding that `<script setup>` declares, not an import or a global. Two pages that each declare `async function reload() { await resource.reload(); if (!resource.loadError.value && resource.data.value) acceptSaved(resource.data.value); }` over their own `resource` and `acceptSaved` were reported as copies, though sharing it would take a one-function module receiving each page's state as arguments, which the client guide warns against. Neither copy counts any more, in the file linted or in the files it is compared with; a pure helper the pages repeat, a closure over imports, one of three statements or more, and one that also reads a global are still reported.
- **Breaking.** `jskit check` fails a Vuetify component named as a string for Vue to resolve at run time (`ui/vuetify-by-name`): `resolveComponent("v-dialog")`, `resolveDynamicComponent("VDialog")`, `h("v-dialog")`, `<component is="v-dialog">` or a string in a bound `:is`, for each component the app's installed Vuetify exports from `vuetify/components` (another library's `v-chart` is not Vuetify's). A JSKIT app registers no Vuetify component globally (vite-plugin-vuetify imports each where a template writes its tag), so the name resolved to nothing and Vue rendered an unknown element: a dialog that never opened. Upgrading: import the component (`import { VDialog } from "vuetify/components"`) and pass it (`:is="VDialog"`, `h(VDialog)`).
- **Breaking.** `jskit check` fails a prop an app passes to a JSKIT component that the installed package lists as removed (`ui/removed-prop`), in camelCase or kebab-case, static or bound, for a component imported from `@jskit-ai/<package>/client/components/<Name>` or by name from `@jskit-ai/<package>/client`: Vue passed it on as an HTML attribute that did nothing, so an upgrade dropped it silently. A package lists its removals as `jskit.metadata.ui.removedProps: { "<Component>": { "<prop>": "<what to do instead>" } }`, and `lint:packages` refuses one for a component the package does not export as `./client/components/<Component>`, or without a hint. Nothing excuses a `ui/*` finding. Upgrading: run `npx jskit check m3` and remove each prop it lists.
- `jskit check`'s data part skips what the app's ESLint config ignores outside server code, as no lint reads it either, and lists each skipped directory (or file, where its directory holds code it reads) under "Skipped". It read every app file but a fixed list of folders, so a read-only vendored copy of old code that the app's config ignores failed on that copy's `eslint-disable` comments (`data/lint-disabled`), and the app could never pass. Server code, as `@jskit-ai/config-eslint` lints it at the app's root or a package's (its files, such as `server.js`, and its `src/`, `server/`, `scripts/`, `bin/` and `config/`), is read and judged whatever the config ignores, and fails `data/lint-config` there: before, only a package's `src/server` or `src/shared` and the app's `server/` failed it, so a config that ignored `scripts/` or `src/jobs/` hid that code from the lint. `jskit test --databases` reads the same files for table resources.
- **Breaking.** Plain `jskit check`, and so every app's verify, fails on the Material 3 guide's visual rules (`m3/*`) as well as its navigation rules (`nav/*`): a raw colour, an MDI icon, an outlined card or sheet, a fixed button height, an in-page `h1` under the app bar's title, a theme with no dark scheme, and an `m3-check` comment that excuses nothing: one that names no Material 3 rule or is not `m3-check: allow <rule> - <reason>` (`m3/allow-rule`), or gives no reason (`m3/allow-reason`). They were a report of `jskit check m3` alone. `jskit check m3` still applies the same rules by themselves, to the whole app or to the given paths, and its summary no longer counts the `nav/*` findings apart. Upgrading: run `npx jskit check m3` and fix what it lists before taking this release; JSKIT's own patterns and templates pass it.
- `jskit test --databases` checks a JSKIT package's declared `foreignKeys` only where the test database has the package's table. node_modules can hold a package whose migrations the app never runs, such as one only a devDependency brings or one left behind, and its keys failed the run as missing. The summary counts the package tables it left out. The app's own table resources are checked whatever the database holds, as before.
- **Breaking (security).** `jskit/no-direct-knex` catches a table a `scopedQuery()` report or a subquery reads past its owner in every form the builder accepts. `from`, `table` and `into` now judge a variable or property as joins did, and every table method (and `knex(...)` and `trx(...)`) judges an alias object (`{ p: "projects" }`, `{ p: PROJECTS_TABLE }`) by its values. A variable or property whose name says table or name (`PROJECTS_TABLE`, `name`, `tables.lots`) names a table, and so does a const that holds one (`const target = "projects"`). In a subquery callback (`whereIn("id", (sub) => sub.from(PROJECTS))`, `whereExists(function () { this.from(source) })`), whose builder is Knex's own and unscoped, any variable but one holding another table's `scopedQuery()` subquery names a table, imports and parameters included. Before, only text was refused in `from`, `table` and `into`, and a join only of a name saying table, so `.from(PROJECTS_TABLE)`, `.from(name)`, `.join({ p: "projects" }, ...)` and `.join(name, ...)` passed though the read-only builder joins any table at run time.
- `jskit/no-transaction-reader` reports a key other than `context` or `trx` read or destructured from the transaction options a work callback receives: `withTransaction(options, work)`'s first parameter and `lockOrCreate(row, options, work)`'s second. Those hold `{ context, trx }` and nothing else, so an application's own key read there (`txOptions.checkout`, or `options.checkout` where work's parameter shadows the method's options) was always undefined: a checkout flag was silently dropped while every server test passed. Read it from the method's own options.
- **Breaking (security).** `jskit/no-hand-context` refuses the resource runtime's `declareSystemScope` called, read or destructured, as it refuses `createSystemContext`: it is how the kernel gives a feature with a `systemScope` its `systemContext`, and called anywhere else it mints a system context for a feature that declared none. JSKIT's own `eslint.config.mjs` turns the rule off for the kernel's `defineFeature.js` only.
- **Breaking (security).** `jskit/allow-comment-form` reports an inline config comment that sets a data-access rule (`/* eslint jskit/no-direct-knex: "off" */`), as it reports an `eslint-disable` naming one; such a comment turned the rule off unseen.
- **Breaking.** The data-access lint rules check an application's own `src/` whole, and tell seeds by their folder or a script's place, not by name. They left `src/` outside `src/server` and `src/shared` alone as client code, and every `seed*.js` anywhere as a seed, so server code in `src/` (a pattern's `src/ApplicationAiFeature.js`, a `src/jobs/` folder) and a `seedService.js` in a server tree escaped every rule. Client code is now a package's `src/client`; seeds are a `seed` or `seeds` folder, or a `seed*` script in a `scripts/` or `bin/` folder or at the root. Client code in `src/` has nothing for the rules to report, so linting it costs nothing.
- **Breaking (security).** `jskit check`'s data part fails a module that requires any capability handing out rows past their owners, from one list: `runtime.database` and `runtime.resources` outside a module declared infrastructure, as before, and now `realtime.audience-scope` (contexts for any workspace and user) and `auth.local.accounts`, `auth.local.sessions` and `auth.local.recovery` (local sign-in's rows, in its system context) until `jskit-data-access.json`'s `systemScopes` lists the file and capability with its reason: `{ "file", "capability", "systemScope": "<reason>" }`. Capability ids are read trimmed and in any case, as the kernel resolves them (`"Runtime.Resources"` was missed), a feature's own `id` requires nothing, and `data/lint-disabled` also fails an inline `/* eslint ... */` config that sets a data-access rule. Its client exception follows the lint: a package's `src/client`, no longer the app's own `src/`.
- **Breaking (security).** `jskit check`'s data part fails an app file that the app's own ESLint config lints without every data-access rule as an error, read with ESLint's `calculateConfigForFile` (`{ rules: { "jskit/no-direct-knex": "off" } }`, a rule lowered to `"warn"`, `dataAccessConfig(files, "off")`), and server code (`src/server`, `src/shared`, `server/`) that the config ignores (`data/lint-config`), until the baseline's `infrastructure` lists that `{ file, rule }`. Each file is judged by the config that governs it, as `eslint` does, and what the rules leave alone (client code, tests, migrations, seeds) is told from that config's directory, so a nested application's own client code passes. An app without an ESLint config is left to its lint run, which then cannot start.
- **Breaking (security).** The cross-owner capabilities also hold `connectors.store` (every owner's connections, credentials decrypted), `assistant.repositories` and `payments.store`. A feature's own id passes only in the file that provides it, so a feature named after a capability it does not provide requires it like any other module.
- **Breaking (security).** `jskit/no-direct-knex` judges both branches of a `?:`, `??`, `||` or `&&` given to `from`, `table`, `into` or a join, and reports every `fromRaw()` and `joinRaw()` outside an infrastructure module, since their SQL names the table. In a subquery callback, a variable destructured from a call (`const { query: recent } = await lots.scopedQuery(...)`, the guide's own pattern) holds a builder, not a table name, and passes.
- **Breaking.** A tests, migrations, seeds, build or documentation folder counts only at the root of the app or of a package (`packages/*`, `tooling/*`), in the data-access lint scope and in `jskit check` alike: such a folder deeper in server code (`src/server/migrations/`, `src/server/test/`) is server code and is checked. A package's `src/test` (its published test helpers) stays outside, as before.

It imports only the modules that declare `foreignKeys` (each must export its resource); an app without `@jskit-ai/resource-runtime` has nothing to check.

An untyped binding still counts as JSKIT's.
- `jskit/sql-literal` takes the whole-file infrastructure exception too (`// readable-check: allow sql-literal - infrastructure: <what the module is>`, before the first line of code), for a module that runs SQL it is given by design, such as a database console's query runner; the data check lists it and requires it in `jskit-data-access.json`. A per-line excuse is still refused.
- The infrastructure exception (`// readable-check: allow <rule> - infrastructure: <what the module is>`, before a file's first line of code) also lifts a whole file past `jskit/no-hand-scope`, for an operator's data import or cutover tool that names each workspace it loads; the data check lists it and requires it in `jskit-data-access.json`, as it does for `no-direct-knex` and `no-transaction-reader`. In a file lifted past `jskit/no-direct-knex`, `jskit/sql-literal` lets raw SQL hold a statement (`UPDATE`, `DELETE`, a join), since it runs on Knex itself rather than inside a scoped query; it is still one literal with its values as bindings. `jskit/no-hand-context` and `jskit/knex-reason` still take no exception.
- `browserTestConfig({ actionTimeout, navigationTimeout })`: an app sets its own bound for one action (15 s) or one navigation (30 s) for a measured need, never none (0 is refused, like `globalTimeout`). The defaults are unchanged and now tested: a stale locator fails in seconds with its own error instead of waiting out the test's 60 s (over 652 passing app tests the slowest action or page load took 9.0 s; without the bounds a stale locator waited 116 to 230 s).
- The local browser run's launcher (`browserTestConfig()`'s webServer) refuses a port that already answers before it builds, prepares or starts anything ("Port 4174 on 127.0.0.1 already answers: ..."). Before, a server an earlier run left there answered the ready check for the new one, the ready line printed, and then the new server failed with EADDRINUSE and the launcher stopped every worker's server mid-run. When the stdin pipe Playwright gives its webServer ends (a Playwright stopped without stopping its webServer, such as one killed on a timeout), the launcher now stops its servers instead of leaving them and itself running. On SIGTERM, SIGINT or that end it waits for its servers to stop, up to 9 s, inside Playwright's 10 s grace, kills any still running, and only then exits; before, it exited at once and Playwright's wait ended before the servers had stopped.
- `browserTestConfig({ signIn })`: a worker of a project that depends on another, such as a setup project, starts from its own server's signed-in state. Playwright gives a dependent project's workers the environment its dependency's workers changed, so with two or more workers each one inherited worker 0's `PLAYWRIGHT_STORAGE_STATE`, took it for a login the host supplied, and sent worker 0's session to its own server: every test on the other workers started signed out. A state among the harness's own `signed-in-<port>-<index>.json` files is no longer taken for the host's.

- `jskit check` lists, as information (it never fails on them), the fields of each of the app's table resources that its CRUD contracts never name, and so that no API shows or accepts (`data/unnamed-fields`): a field a contract should offer is visible there. Ownership fields, stamped timestamps, the primary key and `hidden` fields are left out, and a resource whose contracts spread or compute their `fields` is not judged.
- **Breaking (security).** `jskit check`'s data part fails on what a lint directive could hide, in the app's own code: an infrastructure exception or a feature's system scope that the checked-in `jskit-data-access.json` at the app's root does not list (`{ "infrastructure": [{ "file", "rule" }], "systemScopes": [{ "feature", "systemScope" }] }`), so each new one is reviewed (an app without the file fails on every one it has; a file that is not JSON fails); a module that requires `runtime.database` or `runtime.resources` (names one outside its `provides`) without the infrastructure exception; and an `eslint-disable` that names a data-access rule, or no rule at all, outside client code. - `jskit test` stops a test file that is still running at twice its bound (`fileMs`, or its own in `test-time-bounds.json`; at least two seconds), or sooner at ten times the time it last finished in (at least two minutes), and the run fails naming it ("test/x.test.js was stopped after 2.0 min, past ten times its last time of 5.3 s: it did not finish."), while the other files still run and the report still prints. - `@jskit-ai/jskit-catalog/browser-tests` (new export): `browserTestConfig({ testDir, port, server, build, prepare, env, health, globalTimeout })` returns an app's Playwright configuration. A local run builds the production frontend into `dist/` once, reused while the contents of its inputs (every file at the app's root except other dotfiles and notes, `src`, `packages`, `shared`, `config`, `public`, the installed `@jskit-ai` packages, the build command and `VITE_` settings) and the served `dist/index.html` are unchanged; two runs in one tree build one at a time and the second reuses the first one's build. It runs the app's `prepare` module once for each worker's server environment (its own database), which the worker's own process also gets, and starts one app server per worker on its own port (`PLAYWRIGHT_PORT`, default 4173, plus the worker's index). Workers come from `--workers`, `PLAYWRIGHT_WORKERS` or half of `testConcurrency()`, since each drives a browser and its own app server. With `PLAYWRIGHT_BASE_URL`, the tests use that managed target as its host serves it, one worker unless `PLAYWRIGHT_WORKERS` says otherwise. Every run has a `globalTimeout` (20 minutes unless the suite passes its own measured bound; 0 is refused), 60 s per test, 15 s per action, 30 s per navigation, a failed test's trace without a screencast, and ends with its 10 slowest tests.
- `browserTestConfig({ signIn })` (new option): an app module whose default export `({ request, baseURL, workerIndex, env })` signs each worker's server in once, after the servers start; every test of that worker starts from that server's signed-in storage state (written only this user may read), which the worker's process also finds in `PLAYWRIGHT_STORAGE_STATE`, as on a managed target, instead of each test signing in. A login state the host supplies is used as it is.
- The foundations' `server.js` serves content-hashed files under `dist/assets/` with `Cache-Control: public, max-age=31536000, immutable` instead of `public, max-age=0`, so a page load stops revalidating each script and stylesheet (measured on an application: a warm navigation's DOMContentLoaded 0.8-1.2 s -> 0.2-0.35 s); `index.html` and unhashed files still revalidate. Apps copy the change at their next repin (see Upgrade JSKIT).
- `jskit test` gives the test file processes it starts Node's compile cache, `node_modules/.cache/jskit-node-compile-cache` (`NODE_COMPILE_CACHE`), so each file's process reuses the modules earlier ones compiled; a cache the environment names, or `NODE_DISABLE_COMPILE_CACHE=1`, wins.
- `jskit test` ends with its 10 slowest test files and tests (on stderr), records each file's time in `node_modules/.cache/jskit-test/file-times.json`, and fails when a file took more than 10 minutes or the whole command more than 45, bounds only a clearly broken suite reaches. An app sets its own `runMs`, `fileMs` or per-file bounds in `test-time-bounds.json`; an app with a file that already takes longer than 10 minutes splits that file, or sets its measured bound there, at its repin, so the repin does not fail on it. The time reporter runs beside the run's own reporters (`spec` on stdout when it names none).
- `jskit test` with a `// jskit-test: alone` file and file reporter destinations writes the alone run's reports beside the parallel run's (`junit.alone.xml` beside `junit.xml`) instead of over them, and with `--test-shard=<index>/<total>` picks that shard's alone files itself, as node --test would, so a shard with none no longer starts an empty node --test run. A command that names no file, only options with their values given apart (`--test-reporter junit`), still finds its alone files instead of running every file in parallel.
- `prepareTestDatabases({ schema })` and `testDatabaseRun({ schema })`, and `export const testDatabaseSchema` beside the knexfile's default export for `jskit test --databases`, build a new snapshot's schema with the app's own `build(knex)` instead of `knex.migrate.latest()`, for migrations that start from a baseline schema file or rows every test database starts with; `files` lists what the build reads, and their contents join the snapshot key (`testDatabaseSnapshotKey(knexConfig, { schemaFiles })`). The snapshot's migration list is read from the built database's ledger.
- Test databases on PostgreSQL 15 and later copy the snapshot with `CREATE DATABASE ... TEMPLATE ... STRATEGY FILE_COPY`, which copies the template's files instead of writing every page through the WAL; older servers keep the default.
- `jskit test --databases`: each test file running at once gets its own copy of `TEST_DB_NAME`, restored from a schema snapshot keyed by the migrations and `package-lock.json`, through the app's `knexfile.js` and `@jskit-ai/database-runtime/server/testDatabases`; a focused run prepares one database per file it runs at once. Each test file gets the environment `jskit test` was given plus its database's connection (`DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`); the rest of the `.env` the knexfile loads is read for the databases only, and the runner passes the connection in a file only the user may read, never in its own environment. With TEST_DB_NAME unset, equal to the connected database or not preparable by the database user, the files run one at a time on the connected database; a copy named like a protected database, or an unreachable server, fails the run.
- `@jskit-ai/database-runtime/server/testDatabases` exports `countQueries(knex, work)` for query-count guards: it runs `work` and returns its `result`, the `count` of statements the given Knex instance or transaction sent meanwhile (a transaction's `BEGIN` and `COMMIT` included) and their SQL in `queries`. `countRuntimeQueries(work)` does the same for the application runtime's own `runtime.database`, so a test that boots the server in its process (`createServer()`, `app.inject()`) counts a route's statements; the runtime publishes each statement on the `jskit:database:query` diagnostics channel for it. The typed features guide's query-count tests use them instead of a hand-written `query` listener or a patched Knex client.
- `@jskit-ai/database-runtime/server/testDatabases` gains the data-test helpers of the data-access redesign, built on `countQueries` and `countRuntimeQueries`. `requireTestDatabase(environment)` answers `TEST_DB_NAME`, or throws `TestDatabaseMissingError` ("TEST_DB_NAME is not set; data tests never skip"), so a data test without a database fails instead of skipping. `tableNames(knex)` lists a database's tables. `expectFlatQueries` lives in `@jskit-ai/resource-runtime/test` (see its changelog).
- Plain `jskit check` fails a Playwright config whose webServer runs the development server (`test/playwright-dev-server`), whose workers share one webServer instead of using `browserTestConfig()` (`test/playwright-isolation`), or with no `globalTimeout` or `globalTimeout: 0` (`test/playwright-global-timeout`); a config built by `browserTestConfig()` that sets `workers` itself (`test/playwright-workers`); and a script that pins `V64_TEST_CONCURRENCY` or `PLAYWRIGHT_WORKERS` (`test/fixed-concurrency`).
- A whole-app `jskit check` (and `jskit check m3`) reads only the app code of a `@jskit-ai/*` package under `packages/`, its `patterns` and `templates`, so JSKIT's own repository passes: the framework's packages implement the navigation the rules send apps to (`ShellUpButton`, `reloadAppPage()`, `leaveApp()`, the system Back button, sign-in redirects), and their 20 `nav/*` findings were the implementation itself. An app's own packages keep every rule, and a path given to `jskit check m3` is read as asked.
- `m3/raw-hex` finds colours written as channels too: `rgba(0, 0, 0, 0.15)`, `rgb(0 0 0 / 20%)` and `hsla(...)` in CSS, inline and bound styles, scripts and colour attributes, as in a hand-made `box-shadow`, which passed before. One that reads a theme role with an alpha, `rgba(var(--v-theme-shadow), 0.2)`, passes; `src/theme/` stays exempt.
- `m3/duplicate-h1` counts h1s on different branches of one `v-if`/`v-else-if`/`v-else` chain (a sign-in view's h1 per step, a page's h1 per state) as one title, since only one renders; two h1s that can show together are still a second one.
- `m3/duplicate-h1` judges a page's h1 only under a layout that always renders its pages under the page title. A layout that renders them outside its `ShellLayout` on one branch (a shop device's staff sign-in in a bare `v-main`) leaves them unjudged, as `nav/missing-parent` does: which branch shows a page is decided at runtime.
- `nav/surface-parent` (new): a page or layout whose route meta declares `jskit.parent` beside `jskit.surface` is an error, since the shell reads a page's parent only up to its surface root and so never sees that one (the page shows no Up arrow). It catches a layout and an inner page alike (an inner page repeating its surface is a surface root of its own), and the message says to declare the surface only on the surface's layout page and the parent on the page it renders.
- `m3/duplicate-h1` follows JavaScript importers too: a component `src/main.js` hands the shell to render outside every layout (`notFoundComponent`, a `fallbackRoute`'s component, the `rootComponent`) counts only as `App.vue` does, so a not-found view without a top app bar keeps its `h1`. A component JavaScript routes or places otherwise is still judged as under the title.
- `nav/back-control` flags a back component by its name, in PascalCase or kebab case (`<ContextBackButton />`, `<page-back-link>`, `GoBack`, `BackToList`), without a link or handler at the tag, and its import. A back-to-top control and names such as `BackOffice` are not back components.
- `nav/missing-parent` judges only pages that always render under the shell's top app bar. A layout that also renders its pages without `ShellLayout` (a shop device's sign-in in a `v-if` beside it) leaves which of them show Up unreadable, so none of its pages needs a parent; `nav/top-level-parent` and `nav/missing-shell-layout` still read it as a shell layout.
- `jskit test [node options] [files or globs]` (new): node --test with test files in parallel within the machine's test budget, `V64_TEST_CONCURRENCY` when it is a positive whole number, otherwise half of the machine's CPUs (at least 1). Its arguments go to node --test unchanged; it refuses `--test-concurrency`. A file whose first line is `// jskit-test: alone - <reason>` runs after the others, one such file at a time; a marker without a reason or below the first line fails the run.
- `@jskit-ai/jskit-catalog/test-budget` (new export): `testConcurrency()` returns the same budget for `workers` in `playwright.config` and `maxWorkers` in the Vitest config.
- Plain `jskit check` fails test runs outside the budget (`test/*`): a package script that runs `node --test` directly (`test/node-test`) or passes `--test-concurrency` (`test/fixed-concurrency`), `--workers`/`-j` to `playwright test` or a Playwright config without `workers: testConcurrency()` (`test/playwright-workers`), and `--maxWorkers`/`--minWorkers`/`--no-file-parallelism` to Vitest or a Vitest config without `maxWorkers: testConcurrency()` or with `fileParallelism: false` (`test/vitest-workers`). Each finding links typed features' "Test files run in parallel".
- `nav/placement-data` (new): a main-navigation placement that isn't literal data (built by a helper, spread, interpolated, or with computed props, suffixes or surface) is a finding that says to declare it literally. While one is unreadable, no page is judged for `nav/missing-parent`, instead of each of its destinations being reported as missing a parent.
- `nav/missing-shell-layout` (new): a page that declares a parent but renders under no layout that draws the shell's top app bar (an account page without `src/pages/account.vue`) is a finding, since its title, Up and page actions never show. An `App.vue` that wraps every page in the bar leaves none outside it.
- `m3/duplicate-h1` flags an in-page `h1` only under the shell's page title: in a file that shows it, a page a layout showing it (`ShellLayout`, or `ShellPageTitle` in a bar of its own) renders, or a component such a file imports. A hero front page, an intro, an invite or hand-off page without a top app bar, and the components only they render, keep their `h1`. A component no `.vue` file imports is still judged as under the title.
- `m3/raw-hex` findings name `src/theme/palettes.js`, the sanctioned home of content colours (identity palettes, artwork, brand marks, chart series), which, like the rest of `src/theme/`, may hold hex values.
- `nav/top-level-parent`: a main-navigation link that names its surface (`props.surface`) is a destination of that surface only, wherever it shows, as the runtime resolves it; a Home link also shown on an account surface no longer makes the account page a destination.
- `m3/fixed-button-height` findings say that a smaller button is `size="small"` or `"x-small"`, which keeps the touch target.
- `jskit check` counts a layout that renders shell-web's `ShellUpButton` in a top app bar of its own, directly or through an app component it imports, as a shell layout: its pages need parents and are counted as shell pages.
- `nav/back-control` flags only controls that navigate the app (a link, or a handler that reaches the router, JSKIT paths, `up()`, `finish()` or the browser's history or location, directly or through the component's own functions) and back-named functions that do. Prose, variables, in-page steps and an embedded frame's own history (`contentWindow.history`) are no longer findings. Its messages name `ShellUpButton` for layouts that draw their own bar.
- The navigation rules judge an app's package routes as shell pages: each `packages/<name>/package.json` route in `jskit.metadata.ui.routes` that the kernel registers, with the component its client entry's literal `routeComponents` names. An inner one without `meta.jskit.parent` is `nav/missing-parent`; one a main-navigation link leads to (its suffix on the route's surface, or a link's `to` for a global route) that declares a parent is `nav/top-level-parent`; a parent beside `meta.jskit.surface` is `nav/surface-parent`; and a parent on a route whose component draws no shell bar (nor `App.vue`) is `nav/missing-shell-layout`. Findings point at the route's entry in `package.json`. A run over a package's files judges its routes too. A main-navigation link's `to` counts as a destination for page files as well.
- `m3/duplicate-h1` reads a package route's page as the kernel renders it, at the top level: it has the bar's title only when it draws the bar itself or `App.vue` does, so its own h1 is no second one otherwise.
- `jskit update` lists the package migrations its install added, each as `<package>: <file>` from the installed packages' `jskit.migrations.directories` (and their `constraints/`), and says to run `npm run db:migrate` before the app serves requests: a new package version that reads what its migration creates fails until then, as local sign-in's account reads do on a database without `auth_local_users.email_verified_at`. With `--no-install` it adds that, if npm install installs new package migrations, `npm run db:migrate` runs before the app serves requests. `updateProject()` answers them as `addedMigrations`.
- `jskit/no-transaction-reader`, for a transaction read that an `if` tests before throwing, says which setting replaces the check: `if (!options.trx) throw ...` points to `withTransaction({ ...options, joinOnly: true }, work)`, and `if (options.trx) throw ...` to `withTransaction({ ...options, outermost: true }, work)`. Both settings ride in options, so the rule finds nothing in them.
