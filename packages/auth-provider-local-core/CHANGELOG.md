# Changelog

## Unreleased

- Each sign-in and each refused one is an event for the new optional `auth.local.sign-in-events` capability (`AuthLocalSignInEvent`, `AuthLocalSignInEvents`, also `createLocalAuthService({ signInEvents })`), for an application's list of an account's sign-ins or its audit log: `signedIn` or `failed`, the `method` (`password`, `registration`, `confirmation`, `recovery`, `pass`, or `provider` with the provider's id), a refusal's `reason` (`invalidCredentials`, `locked`, `unconfirmed`, `disabled`), the account's `userId` ("" when the email names none), the `email`, the request's `ip` and `userAgent`, and the time `at`; never a password, secret or token. It is given each event after the request has answered, through the deliveries the emails use, so a refused sign-in takes the same time whatever the recorder does; a recorder that fails is logged (`Sending the sign-in event failed.`), and a stopping server waits for the events still being handed over, as for the emails. Without one, local auth logs each event (`createLoggedSignInEvents`, new). A pass that names no account, and a provider callback refused before it names one, are not events.
- Upgrading: `createLocalAuthService()` takes `signInEvents` and refuses, with a `TypeError`, to be made without it; pass `createLoggedSignInEvents(logger)` for the logging the provider uses by default.
- A session keeps where and when it was last seen: `ip` (the request's address), `userAgent` (its `User-Agent`, at most 512 characters) and `lastSeenAt`, each "" when unknown. Signing in sets them from the request that signs in (`login`, `register`, `confirmRegistration`, `completePasswordRecovery` and `signInWithPass` take it as their second parameter, as `oauthComplete` and `devLoginAs` already did; auth-core's actions pass it), and authenticating a request that finds the session more than five minutes after it was last seen sets them again, so most requests write nothing; a request that does not say where it comes from keeps the address and browser. `authenticateRequest` still reads the session once. `createLocalAuthRegisterHookDecorator` passes the request on. Upgrading: a custom `auth.local.backend` keeps a session's `ip`, `userAgent` and `lastSeenAt` from `sessions.create` and implements `sessions.touch(sessionId, { lastSeenAt, ip, userAgent })`, which keeps the old `ip` or `userAgent` when the new one is ""; the file backend adds them to each line of `sessions.passwd` and reads the lines it wrote before as never seen; an application's own auth service decorator around `login`, `register`, `confirmRegistration` or `completePasswordRecovery` passes the request on, or its sessions keep no address.
- A disabled account's sign-in that proves who it is is told the account is disabled, with the application's own message when it gave one: the right password, a linked provider's sign-in or a one-time pass is refused with 403 `auth.local.login.disabled` (new message key `jskit.auth.local.login.disabled`, "This account is disabled.") and the account's `disabledMessage` as its text when it has one, which the sign-in page shows as written. Before, the right password answered "Invalid email or password.", a provider "This account can't sign in." (`auth.local.oauth.accountUnavailable`, still the answer for an identity whose account is missing) and a pass `auth.pass.unmapped` (still the answer for a pass that names no account), so a suspended person could not be told why. A wrong password for a disabled account is still an ordinary failed sign-in, counted by the sign-in throttle, so only someone who could sign in learns that the account is disabled. A backend's users carry `disabledMessage`; the file backend keeps none. `@jskit-ai/auth-provider-local-db-core`'s `auth.local.accounts.disable` and `enable` set and clear it.
- **Breaking:** an installed `auth.local.confirmation-sender` or `auth.local.recovery-sender` sends as `APP_ENV` says, through the kernel's `deliverMessage`: production sends each email to its address; staging sends it only to `STAGING_EMAIL_TO`, calling the sender with that address as `email` and the person's address as the new `originalEmail` (show it, for example with `markStagingEmail`), and logs it, link included, when `STAGING_EMAIL_TO` is unset; development and test log it. This replaces the simulated senders a test copy used, and `createSimulatedConfirmationSender` and `createSimulatedRecoverySender` are gone. Staging and production (`APP_ENV`), not `NODE_ENV=production`, require `AUTH_LOCAL_SESSION_SECRET`, ask for the first account's setup code, refuse `AUTH_LOCAL_RECOVERY_DEV_OUTPUT` (`… is for development only and APP_ENV is staging. Remove it from the staging environment.`) and need a confirmation sender while anyone may register.
- Security: asking for a password reset (`requestPasswordReset`) or a new confirmation link (`resendRegisterConfirmation`) no longer tells, by how long it takes, which emails have an account or a waiting registration. Both answered the same text for any email, but only for one with an account did they write a new link and wait for the sender, so the time of the answer showed whether the account existed, and a sender's failure reached only an account's requester. Each now validates the email, answers at once, and then looks the account up, writes the link and calls the sender; a sender's rejection is logged as an error with the address (never the link) instead of answered. The email is still sent, rate limits and texts are unchanged, and a stopping server (`AuthLocalProvider` now has a shutdown) waits up to 10 seconds for the emails still being sent. Development's `AUTH_LOCAL_RECOVERY_DEV_OUTPUT=response` and a confirmation link shown in development's answer still find the account first, since their answer carries the link; a new registration's link is still sent before its answer, which already says whether the email is taken. Upgrading: an application whose recovery sender reported delivery failures to the requester (a 502 or 503 from `requestPasswordReset`) now has them only in its log; a test that composes `createLocalAuthService()` and reads the sent email waits for it, passing `deliveries: createLocalDeliveries({ logger })` (new export) and awaiting `deliveries.settled()`.
- Security: a failed sign-in takes as long whether or not its email has a password to check. A sign-in for an unknown email, a disabled account or one created through a provider checked no password, while one for an account with a password ran the password strategy's check (scrypt by default), so its time showed which emails had accounts. It now checks the password against a record made once from a random password, through the application's password strategy. Answers, the sign-in throttle and successful sign-ins are unchanged.

- An account made by an email confirmation link has its email confirmed: `confirmRegistration` creates it with `emailVerifiedAt`, the moment its link was used, which the link sent to the email proves, and the database backend keeps it (the file backend keeps no confirmation time, as before). Until now only `auth.local.accounts.markEmailVerified` set it, so every account confirmed by link read as unconfirmed (`emailVerifiedAt` "").

- The pass comes from `@jskit-ai/auth-pass/server`, a new dependency, instead of auth-core's removed `./server/passSignIn`; `AuthLocalPassIdentity` takes auth-pass's `AuthPass`. Pass sign-in behaves as before, with the same refusals and texts.

- One-time pass sign-in: with `AUTH_PASS_PUBLIC_KEY`, `AUTH_PASS_AUDIENCE` and `AUTH_PASS_RESOURCE` set, `signInWithPass({ pass })` checks a pass from `@jskit-ai/auth-core/server/passSignIn`, records it as used, and signs in the account the new `auth.local.pass-identity` capability names for it (`AuthLocalPassIdentity`, also `createLocalAuthService({ passIdentity })`); startup stops when the key is set and no mapping is installed. Each pass signs in once: the backend contract gains `passes.use({ id, expiresAt })` and `passes.deleteExpired(now)`, keyed by the hash of the pass's id and kept until 30 seconds after it expires, and the file backend keeps them in `passes.passwd`. Without the key, `signInWithPass` is refused as unsupported and nothing else changes.
- A dev sign-in (`devLoginAs`), a password sign-in, a recovery link's sign-in and a display-name change hold one database connection at a time. Each read or synchronized the application's profile inside local auth's transaction, and the profile projector (users-core's) reads and writes on a connection of its own, so one request held two pool connections, and as many such requests at once as the pool has connections each held one and waited for ever for another. The profile is now read or synchronized after local auth's transaction, as registration, OAuth sign-in and email confirmation already did; a dev sign-in finds its user in one transaction, reads the profile, and only then creates its session in another, so a user without a profile still gets none. Should synchronizing the profile fail after a sign-in's transaction committed, the sign-in still fails and its session is never handed out (it expires), as for a registration; a recovery link is then used up, and a changed display name stays changed until the next request's profile check synchronizes it.
- `AUTH_COOKIE_SAME_SITE=strict` makes every local auth cookie SameSite=Strict, and its clearing: the access, refresh, recovery and OAuth attempt cookies. Unset, blank or `lax` keeps them Lax, as before; any other value stops startup, naming the setting. OAuth sign-in works under `strict`: the provider's cross-site return only loads the login page, and the attempt cookie is read by that page's same-origin `POST /api/oauth/complete`. `resolveLocalAuthConfig()` returns `cookieSameSite`.

- **Second factor: authenticator-app codes (TOTP, RFC 6238) with recovery codes**, one per account, in the file backend and through the backend contract. Setting up shows the secret once (as text and in an `otpauth://` address for a QR code, whose issuer is `APP_PUBLIC_URL`'s host) and a first code confirms it, answering ten single-use recovery codes once. A code is six digits of a 30-second step, accepted within one step either side of the server's clock and only once: no code of an accepted step or an earlier one passes again. The secret is sealed with AES-256-GCM, bound to its account, under a key derived from `AUTH_LOCAL_SECOND_FACTOR_KEY`; recovery codes are kept as keyed hashes. An accepted code or recovery code marks the request's session with the time (`secondFactorAt`, which `authenticate` returns for the auth policy); removing the authenticator clears it from every session of the account. Wrong codes make the account wait as wrong passwords do (five, then 30 seconds doubling to an hour), refused with 429 `auth.local.secondFactor.locked`. New refusals, each with its message key under `jskit.auth.local.secondFactor`: `notSetUp`, `alreadySetUp`, `setupNotStarted`, `proofRequired`, `codeInvalid`, `codeUsed`, `recoveryCodeInvalid` and `locked`.
- Every second-factor change and failed attempt (setup started or confirmed, verified, failed with its reason, recovery codes replaced, removed, reset) is an event, with the account id, the request's address and the time and never a secret or a code, for the optional `auth.local.second-factor-events` capability (`AuthLocalSecondFactorEvent`), an application's audit log; without one, local auth logs each event. `listSecondFactors({ userIds })` and `resetSecondFactor({ userId, byUserId })` serve an application's own owner screens.
- Upgrading: a production server has a second factor only with `AUTH_LOCAL_SECOND_FACTOR_KEY` set (at least 32 characters, which then also requires `APP_PUBLIC_URL`); outside production the session secret stands in for it. Keep the key: a factor sealed under one key does not open under another, and verifying one then fails as a server error. A custom `auth.local.backend` implements the `secondFactors` collection (`find`, `findMany`, `save`, `delete`) and `sessions.markSecondFactorProved` / `sessions.clearSecondFactorForUser`, and keeps a session's `secondFactorAt`; the file backend keeps the factors in `second-factors.passwd`.
- An application can confirm a new account at once, without a link, when it chooses to, for example while its email isn't set up: it installs the optional `auth.local.confirmation-mode` capability, a function that receives `{ email }` for each registration that would wait for its link and answers `"link"` (send it, as before) or `"without-link"` (create the account and sign the person in at once, with an address nobody proved, and run the register hook). Only that exact answer skips the link; any other answer means a link and logs a warning. The mode sends nothing, so a test copy (`SIDE_EFFECTS` is not `live`) keeps it and registers exactly as the live copy does, while an installed sender is still replaced by the simulated one there, whatever it does: a test copy never sends real email. A production server still needs a sender (or `AUTH_LOCAL_EMAIL_CONFIRMATION=false`). Before, the only way to confirm at once was code that confirmed with the link the application's own sender was given; in a test copy that sender never runs, so the code got no link and registering failed with 500 (`Invalid URL`). Such code moves to `auth.local.confirmation-mode`. Applications without one are unchanged. For direct library composition, `createLocalAuthService()` takes it as `confirmationMode`.
- A test copy (`SIDE_EFFECTS` is not `live`) sends no email: with an installed sender, confirmation and password-reset emails are logged as simulated (with their links) instead of sent. A logged (development) sender is unchanged. Tests that prove an installed sender set `SIDE_EFFECTS: "live"`.
- With email confirmation on, two registrations whose email is already proven sign in at once instead of waiting for a link: one through an invitation a feature's invitation context resolver resolved, still pending, that names the registering email (letter case does not matter) and has not expired (`expiresAt`), whose link reached that address; and the app's first account, admitted by the production setup code only the server's operator can read (`firstAccountSetup.admitRegistration` answers true for it). An invitation passed through as given (no resolver installed), or one whose context names no email, another email or an expiry that has passed, proves nothing: that registration still waits, as does every other sign-up, and development's first account, which needs no code. Signing in with a waiting registration's password is refused as unconfirmed (403 `auth.login.emailUnconfirmed`) whatever `AUTH_LOCAL_EMAIL_CONFIRMATION` says now, where with it off such a sign-in was an ordinary failed one; registering again with it off creates the account.
- Completing a password reset consumes the user's other password resets (`rec_…` tokens) only, leaving an app's own kinds of recovery token, such as sign-in links, open: the backend contract's `recovery.consumeForUser(userId, { idPrefix })` takes the kind it consumes, and the file backend requires it as the database backend does.
- Security: confirming a registration takes the password it was registered with as well as its link's code, `confirmRegistration({ token, password })`. A missing or wrong password creates nothing, keeps the registration and its link, and is refused with 400 `auth.local.register.confirmationPasswordInvalid` (on the `password` field; new message key `jskit.auth.local.register.confirmationPasswordInvalid`). Registering an email again replaces its waiting registration whole, password, display name and invitation included, and a new link from `resendRegisterConfirmation` keeps the registration's password and is no longer sent for an expired registration. So whoever registers an email, before its owner or after, the account its link creates has the password of the person who confirmed it: before, a registration that waited kept its password when the email's owner registered later, so whoever registered first could sign in to the account the owner then confirmed, and the owner's link created no account they could tell apart.
- The file backend refuses a second account with a taken id or email with a `ConflictError` (409) coded `auth.local.accounts.exists` ("An account with this id or email already exists."), where it threw a plain `Error` with no code, so a caller that retries on a duplicate can recognise it.
- The local file backend takes over a store lock left by a crashed process (older than 30 s, its process gone) at its first attempt, instead of after waiting out the 2 s lock timeout. A lock whose process is alive is still never removed, however old.
- A request authenticates once. The route's auth policy and the handlers it runs (`getSecurityStatus`, `updateDisplayName`, `changePassword`, `signOutOtherSessions`, `startProviderLink`, `unlinkProvider`, an OAuth link) share the first `authenticateRequest()` answer for the same request object, instead of reading the session, the user and the app profile again each time. A display name change updates that answer's actor. `logout`, `signOutOtherSessions` and `resetPassword` forget it, so a later check in the same request reads the sessions again. Every new request still reads its session and user, so sign-out, revocation and disabling take effect from the next request. A failed authentication is not remembered, and a `syncProfile: false` check is never shared.
- An ordinary request synchronizes the app profile only when it is missing or its email or display name no longer matches the user (`onlyWhenChanged`); its session and user are still read on every request, so sign-out, revocation and disabling take effect at once. Sign-in, registration and a session refresh (every 15 minutes, when the access token has expired) synchronize in full, which also re-runs workspace provisioning. Measured in apps, every signed-in request ran a second transaction for the sync: GET /api/session 8 statements, GET /api/settings 21 (two authentications), PATCH /api/settings/profile 52. Visible difference: a personal workspace, owner membership or settings row deleted while someone is signed in comes back at their next refresh or sign-in instead of their next request.
- `updateDisplayName` answers the synchronized app profile as `profile`, so users-core no longer writes the users row a second time after a display name change.
- Local auth reports `features.password.selfRegister: false` with `AUTH_LOCAL_SELF_REGISTRATION=false`, so the sign-in page hides its Register tab, except while the app has no account: its first account may register (with the setup code in production), in development too, where the server now checks once at startup whether there is an account.
- `AUTH_LOCAL_SELF_REGISTRATION=false` closes self-registration: an account registers only by an invitation a feature's invitation context resolver resolves for its email, or as the first account (admitted by its setup code in production); anyone else is refused with 403 `auth.local.register.closed` (new message key `jskit.auth.local.register.closed`; an app with other locales adds it with `npx jskit i18n export <locale>`). Confirmation guards self-registration, so with it off a production server starts without an `auth.local.confirmation-sender`, and those registrations sign in at once. Upgrading: an invitation-only or admin-created-accounts app that refused to start in production for want of a confirmation sender sets `AUTH_LOCAL_SELF_REGISTRATION=false` (and can drop its own 404 hook on the register routes); the startup refusal now names this way out too. `resolveLocalAuthConfig()` returns `selfRegistration`.
- The first account of a production server needs a one-time setup code. While local auth has no account, each start of a production server makes a new code, writes it in the log (a warning with `firstAccountSetupCode` and `firstAccountSetupCodeFile`) and in `first-account-setup-code` in `AUTH_LOCAL_STORE_DIR` (mode 600), and keeps only its hash; registering without it is refused with 403 `auth.local.setup.codeRequired`, with a wrong one with 403 `auth.local.setup.codeInvalid`, and an OAuth sign-in cannot create that account. Once an account exists the code stops working and its file is deleted. Development needs no code, and servers that already have accounts are unchanged. `getCapabilities()` says `features.firstAccountSetupCode` while it waits. `AuthLocalProvider` checks for an account as it starts, and `createLocalAuthService()` takes the started `firstAccountSetup` (by default it checks on first use). New exports `createFirstAccountSetup` and `SETUP_CODE_FILE`; new message keys `jskit.auth.local.setup.codeRequired` and `jskit.auth.local.setup.codeInvalid`.
- Upgrading: a custom `auth.local.backend` implements `users.hasAny()`.
- A hosting tool may supply the first account's setup code in `AUTH_LOCAL_SETUP_CODE` (production only; at least 20 letters and digits, or startup stops naming the variable) and show it to the operator itself. The server then asks for that code at every start and on every server, writes no `first-account-setup-code` file (it deletes one left behind), and logs only that the code is in `AUTH_LOCAL_SETUP_CODE` (`firstAccountSetupCodeEnv`), never the code. New export `SETUP_CODE_ENV`. The refusal and sign-in texts name the server's log or its hosting service.
- Registration confirms the email address, on by default in every environment; `AUTH_LOCAL_EMAIL_CONFIRMATION=false` turns it off. Registering keeps the registration waiting, with no account, profile or session, and answers `requiresEmailConfirmation: true`; the link's code is random, kept only as a hash, works once, expires after a day and is replaced by registering again or `resendRegisterConfirmation`. `confirmRegistration({ token, password })` creates the account and signs the person in, and the register hook runs then. Signing in with the right password while the registration waits is refused with 403 `auth.login.emailUnconfirmed`. The optional `auth.local.confirmation-sender` (`({ email, confirmationUrl }) => Promise<void>`, which needs `APP_PUBLIC_URL`) emails the link; in development without one, the link is in the answer's `confirmationUrl` and the log; in production without one, startup stops, naming both ways out. Existing accounts are confirmed. New message keys: `jskit.auth.local.register.confirmationInvalid` and `jskit.auth.local.register.confirmationResent`.
- Upgrading: a production app installs an `auth.local.confirmation-sender` or sets `AUTH_LOCAL_EMAIL_CONFIRMATION=false`. Tests that register and expect a session confirm with `confirmationUrl` or set `AUTH_LOCAL_EMAIL_CONFIRMATION=false`. A custom `auth.local.backend` implements the `registrations` collection (`save`, `findByEmail`, `findByTokenHash`, `delete`, `deleteExpired`); the file backend keeps it in `registrations.passwd`, and `@jskit-ai/auth-provider-local-db-core` in the table `auth_local_registrations`, created by its migration `auth_local_db_protection` (run `npm run db:migrate`). `resolveLocalAuthConfig()` takes `emailConfirmationSender`, and `createLocalAuthService()` requires `confirmationSender`: the installed sender, or `createLoggedConfirmationSender(logger)` when there is none.
- A production server (`NODE_ENV=production`) with `AUTH_LOCAL_RECOVERY_DEV_OUTPUT` set refuses to start and names the setting to remove, instead of quietly ignoring it; production recovery stays email only. Upgrading: remove `AUTH_LOCAL_RECOVERY_DEV_OUTPUT` from production environments.
- Failed sign-ins slow down the account they name, existing or not: after `AUTH_LOCAL_SIGN_IN_FAILURES_BEFORE_WAIT` (5) failures in a row the email waits `AUTH_LOCAL_SIGN_IN_FIRST_WAIT_SECONDS` (30) before its next attempt, and each further failure doubles the wait up to `AUTH_LOCAL_SIGN_IN_MAX_WAIT_SECONDS` (3600). While it waits, sign-in is refused, even with the right password, with status 429, the code `auth.local.login.locked` (`params.count` minutes, `params.retryAfterSeconds`) and `Retry-After`. A successful sign-in or a completed password reset forgets the failures, and so does a day without one, so a wait is never permanent and recovery always lets the owner back in.
- `AUTH_LOCAL_PASSWORD_MIN_LENGTH` (default 8, from 8 to 64) sets the shortest password accepted on registration, reset and change.
- Upgrading: a custom `auth.local.backend` implements the new `signInFailures` collection (`find`, `save`, `clear`, `deleteBefore`); the file backend keeps it in `sign-in-failures.passwd`, and `@jskit-ai/auth-provider-local-db-core` in the table `auth_local_sign_in_failures`, which its migration `auth_local_db_protection` creates (run `npm run db:migrate`). `validatePasswordInput(password, minLength)` takes the minimum length.
- New message key: `jskit.auth.local.login.locked`.

## 0.2.0 - 2026-10-29

- Translation ready: every user-visible text is a message key with its English in `locales/en.json`, so an app translates it by supplying translation files only. With no translations, texts and behaviour are unchanged. See the guide "Translating a JSKIT app".
