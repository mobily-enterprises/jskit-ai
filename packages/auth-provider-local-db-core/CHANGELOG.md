# Changelog

## Unreleased

- A user's waiting email change, in the new nullable column `auth_local_users.pending_email` (migration `auth_local_db_users_pending_email`; run `npm run db:migrate`), behind the backend contract's `pendingEmail`, `users.updatePendingEmail` and `users.updateEmail`. Changing the email clears the waiting change and sets `email_verified_at`, which the link sent to the address proves; an email another account has is refused with `auth.local.accounts.exists`.
- Sessions keep where and when they were last seen, in the new nullable columns `auth_local_sessions.ip`, `user_agent` and `last_seen_at` (migration `auth_local_db_sessions_metadata`; run `npm run db:migrate`), behind the backend contract's session fields and `sessions.touch`. `auth.local.sessions.listForUser(userId, options)` answers an account's sessions that are neither revoked nor expired, the newest first, every one of them in one read, each with `ip`, `userAgent` and `lastSeenAt`, and refuses a missing id with a `TypeError`: for an application's list of a person's sessions, its own or an operator's.
- `auth.local.accounts` can disable an account and enable it again: `disable(userId, { message }, options)` refuses every sign-in and session of the account from its next request, and a sign-in that proves who it is (the right password, a linked provider or a one-time pass) is refused with 403 `auth.local.login.disabled` and `message`, at most 500 characters, as its text, or "This account is disabled." without one; `enable(userId, options)` lets it sign in again and clears the message. Both answer the account, now with `disabledMessage` ("" when it has none), or null when there is no such account, and refuse a missing id, or a message that is not text of at most 500 characters, with a `TypeError`. Neither revokes sessions (`auth.local.sessions.revokeForUser` does). Until now nothing set `disabled`. Upgrading: run `npm run db:migrate` for the new migration `auth_local_db_users_disabled_message`, which adds the nullable `auth_local_users.disabled_message` column.
- Its tests name `APP_ENV`, which local auth now reads in place of `NODE_ENV`.
- A new account keeps the `emailVerifiedAt` it is created with (`users.create`), as local sign-in's email confirmation now gives it; without one it stays empty, as before.
- Used one-time passes in the database: the table `auth_local_used_passes` (the hash of each pass's id, until it expires), created by the new migration `auth_local_db_used_passes`, behind the backend contract's `passes` collection, so a pass one server accepted is refused by every server on the database. Two first uses at once both find no row, and the later one's duplicate entry runs its transaction again, which finds it. `LOCAL_AUTH_DB_TABLES.passes` names the table, which the package owns.
- The package manifest no longer requires `runtime.actions`: its feature declares no actions, so since the kernel's 9646ecf21 it does not require the action catalogue, and the catalog's manifest check reported the requirement as one no server provider has.
- Second factors in the database: the table `auth_local_second_factors` (one row per account, deleted with it) and the sessions' `second_factor_at` column, created by the new migration `auth_local_db_users_second_factors`, behind the backend contract's `secondFactors` collection and `sessions.markSecondFactorProved` / `sessions.clearSecondFactorForUser`. `LOCAL_AUTH_DB_TABLES.secondFactors` names the table, which the package owns.
- `auth.local.recovery.consumeForUser(userId, { ...options, idPrefix })` consumes only the user's open tokens whose id starts with `idPrefix`, such as `"rec_"` for a password reset's, and requires it (a `TypeError` without one). It consumed every open token of the user, so an app's new sign-in link (its own `magic_…` tokens) cancelled an outstanding password reset, and a reset its links. The prefix is compared exactly, never as a LIKE pattern, through the recovery table's new server-only `idPrefix` filter. The backend's `recovery.consumeForUser(userId, { idPrefix })` takes it too.
- `auth.local.sessions.update(sessionId, changes, { ...options, onlyIf })` changes the session only while it still has the `onlyIf` values (`userId`, `purpose`, `revokedAt`; others are refused), compared in the one UPDATE, and answers null, writing nothing, when it is missing or no longer matches. An app promotes a sign-in link's session with `onlyIf: { userId, purpose: "recovery", revokedAt: null }` instead of updating it unconditionally and checking afterwards. Its tests run on SQLite, MariaDB/MySQL and PostgreSQL (`tokenKinds*.test.js`; the PostgreSQL one in CI's PostgreSQL job).
- Its table resources declare the foreign keys their migrations create (`foreignKeys`), so json-rest-api 3.1.0 can skip the visibility query a system-context read makes for a record such a key guarantees exists. `jskit test --databases` checks each against an app's test database: auth_local_sessions.user_id and auth_local_recovery.user_id to auth_local_users. `localAuthRecords.mysql.test.js` proves the declarations match the migrations on MariaDB.
- The owner APIs (`auth.local.accounts`, `auth.local.sessions`, `auth.local.recovery`) hand their records only the caller's transaction, with the feature's system context: a caller's other settings no longer ride into every read and write the records make.
- `@jskit-ai/database-runtime` and `@jskit-ai/resource-runtime` are peer dependencies, required and at the same versions, where they were dependencies: its accounts, sessions and sign-in records are table resources, and the app holds one copy of the table runtime that every package shares, as it does the kernel. npm installs a required peer as it installed the dependency, so an app installs the same packages and versions; a release whose versions disagree now fails the install with ERESOLVE instead of nesting a second copy.
- `auth.local.accounts.create` (and the database backend's `users.create`) refuses a duplicate account with a `ConflictError` (409) coded `auth.local.accounts.exists`, carrying the database error as its `cause`, where it threw a plain `Error("Local auth user already exists.")` with no code.
- `AuthLocalDatabaseBackendProvider` declares a system scope ("local sign-in keeps its own accounts, sessions and tokens, which no user owns"), and `auth.local.backend` and the owner APIs run every read and write in its system context, whatever context a caller passes: local sign-in writes its own records, timestamps included. A handle call without a context is now a request's, whose timestamps the handle replaces, so this keeps the times local sign-in writes (a session revoked at its own time, a recovery token created with its account) exactly as before.
- `./server/lib/index` exports `LOCAL_AUTH_INFRASTRUCTURE_TABLES` (`auth_local_identities`), the one table local sign-in keeps outside table resources, for an app test's `expectEveryTableOwned({ infrastructureTables })`.
- New owner capabilities, provided by `AuthLocalDatabaseBackendProvider` beside `auth.local.backend`, for application code that works with local auth's records: `auth.local.accounts` (`create`, `findByEmail`, `updatePassword`, `updateProfile`, `markEmailVerified`), `auth.local.sessions` (`create`, `revoke`, `revokeForUser`, `deleteExpired`) and `auth.local.recovery` (`create`, `findByTokenHash`, `consume`, `consumeForUser`). Each method takes `options` last and runs in `options.trx` when there is one. Their types are `AuthLocalAccounts`, `AuthLocalSessions` and `AuthLocalRecovery` in the new `./server/types`; `./server/lib/index` also exports `createLocalDbOwners`.
- `markEmailVerified(userId, options)` records that the account proved it owns its email address, keeping the first proof, and answers the account; account records answer `emailVerifiedAt` (empty until then). The new migration `auth_local_db_users_email_verified` adds the nullable `email_verified_at` column to `auth_local_users` when it is missing.
- `deleteExpired(now, options)` deletes the sessions that expired by `now` and answers how many.

### Upgrading

- Run `npm run db:migrate` before the new version serves requests: every session read selects `second_factor_at`, so until the migration `auth_local_db_users_second_factors` has run every signed-in request fails with an unknown column.
- Run `npm run db:migrate` before the new version serves requests: its account reads select `email_verified_at`, so until the migration has run every sign-in and account read fails with an unknown column. An application that added `email_verified_at` itself keeps its column (the migration leaves an existing one alone) and replaces its own writes with `markEmailVerified`.
