# Changelog

## Unreleased

- A CRUD list asked over HTTP with a `dateRange` or `numberRange` filter (`filter[arrival]=2026-03-01..2026-03-31`, `filter[total]=15..35`) answers exactly the rows inside the range, where it answered 400: the list action read the route's parsed `{ from, to }` again and refused it (`@jskit-ai/resource-crud-core` now takes it), and past that `toJsonRestQuery` dropped it. A malformed range still answers 400. A `date` or `dateRange` filter's search keys (`__jskit_<key>_from`, `__jskit_<key>_toExclusive`) now hold the day's start as ISO 8601 in UTC (`2026-03-01T00:00:00.000Z`, was `2026-03-01 00:00:00`), the form json-rest-api's `dateTime` search keys take: the old form was refused with 422, so a date filter never filtered through `jsonRestSearchSchema`. `listFilterRoutes.test.js` lists orders over HTTP through a filter contract's route and action validators, search schema and `toJsonRestQuery`, on SQLite.
- A CRUD list or view takes a sparse fieldset for a record its includes reach below their first level, so `?include=customer,customer.region&fields[regions]=name` narrows the included regions where it answered 400. Such a `fields[<type>]` names only the fields and links the contract's `includeFields` lists of that type there, by every path that reaches it, and refuses any other field with a 400 coded `crud.query.fieldsNotShown` that names what it shows; a type no include reaches stays refused (`crud.query.fieldsKeysInvalid`, whose allowed keys now list the types reached). The includes still decide what an included record shows: a fieldset only narrows it. Types the contract links to directly keep taking any field name, as before. Only the tables an include crosses name such a type, so `CrudContractsProvider` resolves the types each contract's includes reach when it seals the registry at boot (`resolveIncludedTypes`, which was `checkIncludedFields` and still refuses a link listed as a field; `contracts.includedTypes(crud)`), and the list and view actions check those fieldsets when they run: `createJsonApiFieldsetsQueryValidator({ resource, deferIncludedTypes: true })` lets such a key through to `createIncludedFieldsetsCheck(resource)`, and without `deferIncludedTypes` refuses it as before. A test proves the narrowing and both refusals through the actions and over HTTP.
- Depends on json-rest-api 3.1.4 exactly (from 3.1.3), from the registry with its published integrity: a patch, put or patchMany that stores the values a row already holds answers the row as stored on MySQL and MariaDB (it answered the values this transaction first read), and AnyAPI storage checks its tables' columns with one statement at start-up.
- A CRUD list asked over HTTP for two or more values of a filter that takes several (`recordIdMany`, `enumMany`, and the list's `id`) answers the rows matching any of them, where it answered 400 (`@jskit-ai/resource-crud-core` reads the comma-separated value the route makes of them). The list's `id` passes the undeclared-key check, which a test proves.
- **Breaking.** A CRUD list refuses a query key its route does not take with a 400 coded `crud.query.undeclaredKeys`, naming the key and the keys the list takes. Fastify's validation dropped an undeclared key without a word, so `?filter[status]=open` on a list that declares no `status` filter answered every row as if it were unfiltered. Upgrading: declare the filter in the feature's `listFilterQueryValidator` and the resource's searchSchema, or stop sending it.
- Every CRUD list takes `id`, one record id or a list of them (`filter[id]` over JSON:API), and answers only those records within the caller's scope, so a client reads the records behind ids it already holds, such as a lookup's selected values past the loaded page, in one request.
- Depends on json-rest-api 3.1.3 exactly (from 3.1.2), from the registry with its published integrity: a write checks each linked target type with one read of the targets' ids (their minimal records only for a target resource with a `checkPermissions` hook), which also takes the shared lock on the belongs-to and polymorphic targets it stores, before `beforeSchemaValidate` rather than after the `beforeDataCall` hooks; in a system context a belongs-to its declared foreign key protects is left to that key, so a missing target there fails with the database's foreign key error instead of `not_found`. json-rest-api now asks for json-rest-schema ^1.0.20.
- Depends on json-rest-api 3.1.2 exactly (from 3.1.1), from the registry with its published integrity: json-rest-api bounds a blob field itself too (`maxBytes` required, a blob answered only where `fields` names it, at most 16 MiB of named blobs per read, none in an include, `queryAll` or HTTP response, many-row write statements chunked by blob bytes, and the MySQL/MariaDB column type chosen by `maxBytes`), its `contains`, `startsWith` and `endsWith` filters match `%`, `_` and `\` literally on every database, a relationship write checks and locks each related type's targets in one query, and an AnyAPI many-to-many read costs its own link rows instead of growing with the square of them.
- A patch naming a linked record that does not exist (a `lookup` field's id with no such row) is refused as that record missing, the error json-rest-api raises with its `resourceType` and `resourceId`, where the CRUD service answered `404 Document not found.` as if the patched record itself were missing. View, patch and delete still answer the 404 (or null for delete) for their own record missing or out of scope.
- A CRUD contract whose `includeFields` lists a link of the included record as a field is refused at boot, at every depth, with an error that names the form to use: a belongs-to field by its key (`"locationId"`) or its relationship (`"location"`), or a collection relation. A JSON:API document answers a link under the record's relationships, never among its attributes, so such an entry never showed and the included record read as if it had no link, which emptied an app's board grouped by it. List it as `{ location: [] }`, which answers the linked id, with the fields to show of the linked record inside it. `CrudContractsProvider` checks every registered contract when it seals the registry at boot, once every feature owns its tables, against the table resources `runtime.resources` answers; a level whose table no feature owns is left alone.
- Depends on json-rest-api 3.1.1 exactly (from 3.1.0), from the registry with its published integrity: a sort on the ID, or on a required attribute stored in its own table, carries no null placement, so PostgreSQL and MariaDB read a descending page from an index instead of sorting every matching row.
- Depends on json-rest-api 3.1.0 exactly (from 3.0.1), from the registry with its published integrity: `lockMode: "noKeyUpdate"`, ON CONFLICT on the matching unique index's exact columns, the PostgreSQL merge race on an uncommitted insert, and the `xid8` field type the change horizon reads.
- `defineCrudFeature` refuses a table resource with ownership `system`, which only a system context reaches: a CRUD surface serves requests, so the owner serves what a request may see through its own methods instead.
- The package's data tests run on `createPackageTestKnex`, so CI's `DB_CLIENT=pg` run proves the CRUD paths on PostgreSQL too.
- A CRUD feature builds its routes and its actions' definitions (their input schemas, channels, permissions and assistant extensions) once per `defineCrudFeature` definition, when a composition first needs them, and every later composition and boot reuses them; each CRUD contract's record and include shapes, which its services read, are worked out once per contract. They depend only on the definition and the frozen contract, so what a composition answers is unchanged, and a build that throws keeps nothing, so every composition that reaches it fails as the first did. Rebuilding them took most of each composition's time: an app of 24 CRUD features composed about six times faster after the first composition (around 84 ms each, from around 500 ms, on one host, back to back).
- **Security.** A CRUD feature's capability repository answers `joinSource({ alias, filters }, options)`, the table as a join source with the columns a read answers and never a hidden one, and, outside a system context, refuses any call whose `fields` names a hidden field, whatever the method, and any method answering another query builder: a join source `decorateRepository` built on `scopedQuery()`, which carried every column, becomes the handle's `joinSource`. A feature whose owned tables hide a field in one and show a field of that name in another fails to start (see `@jskit-ai/resource-runtime`).
- Depends on json-rest-api 3.0.1 (from 3.0.0), exactly, as `@jskit-ai/resource-runtime` does: see its CHANGELOG for the concurrent-merge fix.
- **Security.** A CRUD feature's capability repository answers without hidden fields through every method it holds, the ones `decorateRepository` adds included, for every table the feature owns, unless the call runs in a system context: a custom read that forwarded the caller's `fields` handed hidden values to other features.
- **Security.** A CRUD feature's capability repository (`resourceApi.repository`) on a table with hidden fields refuses another feature's `scopedQuery()` unless it runs in a system context, as it refuses a read naming a hidden field: the builder carries every column. An owner answers its rows to another owner's report through a join source method of its own.
- A custom action whose name breaks the action-name rule is refused with the rule itself: lower case, starting with a letter, with only letters, digits, `_`, `.` and `-` (`cancel-day`, not `cancelDay`). The error said only that the name was invalid.
- `@jskit-ai/resource-runtime` is a peer dependency, required and at the same version, where it was a dependency: every CRUD feature owns its table through it, and the app holds one copy of the table runtime that every package shares, as it does the kernel. npm installs a required peer as it installed the dependency, so an app installs the same packages and versions; a release whose versions disagree now fails the install with ERESOLVE instead of nesting a second copy.
- A CRUD feature's repository (`resourceApi.repository`), which other features and the feature's own actions call, refuses a read whose `fields` names a hidden field of the table unless it runs in a system context (resource-runtime's `withoutHiddenFields`). The handle `decorateRepository` receives answers hidden fields to the owner's own methods, and the CRUD service, the HTTP edge, answers JSON:API documents that never carry one. Before, no handle read answered a hidden field at all.
- The CRUD service hands its repository, or a `decorateRepository` over it, exactly `{ context, trx, format: "jsonapi" }`: no `missing: "skip"` on view or delete, which a decorator passing its options to another table turned into a null for a missing record. View answers the same 404 for a missing record by catching the not-found error, and delete answers null for one.
- A record a form saves back through the CRUD service as the service showed it keeps its link to a target the writer cannot see (json-rest-api 3.0.0): the `null` the read showed counts as unchanged.
- **Breaking (security).** The CRUD service answers records with only the attributes the CRUD contract's output names, on list, view, create and patch, where it answered every column json-rest-api returned whatever the contract said. The actions, routes and a `decorateService` built on the default service answer the same; server code calling the repository still gets whole records. An `include`d record shows only its id, its relation's `labelKey` and what the including contract lists in that field's `output.includeFields`: its fields, and, as `{ relationship: [...] }`, a record it links to with what that shows, at any depth (for example `petId: { output: { required: false, includeFields: ["name", { breed: ["name"] }] } }` for `?include=pet,pet.breed`); another table's contract, which another surface or permission may serve, never shapes it, so an admin contract that shows a person's email never shows it in a member feature's `?include=owner`. A relationship the contract does not name is left out, and an included record only that relationship reaches is not answered. `crud.contracts`, a registry crud-core's new `CrudContractsProvider` provides, holds the served contracts: each CRUD feature registers its contract during setup, the registry is sealed at boot, it refuses two different contracts under one namespace, saying so, and registers a contract served on several surfaces once. The internal `createCrudService` takes `{ repository, crud }` in place of `{ repository, resourceName }`. **Upgrading:** a package with a CRUD feature lists `crud.contracts` in its descriptor's `capabilities.requires`; a test runtime that starts CRUD features adds `CrudContractsProvider` (`@jskit-ai/crud-core/server/crudContracts`).
- The CRUD service no longer stamps `createdAt` and `updatedAt` itself, and `createCrudService` no longer takes `schema`: the handle stamps them on every write. A request cannot set them: a create body's `createdAt` or a patch body's `updatedAt` gives way to the server's time (the CRUD contract no longer takes them either).
- **Breaking.** `defineCrudFeature` fails at once on code written for the earlier CRUD API, naming the replacement, instead of ignoring it. It refuses an option it does not take (`ownershipFilter` is now `visibility`; `searchSchema`, `rowPolicy`, `queryFields` and `hooks` go in an `owns` entry; `resource` is now `crud`), a permission for an action the feature does not define (`patch` is the `update` action) or under any but the lower-case name it is read by, a decorated repository or service that still defines a method of the earlier API (such as `queryDocuments()` or `updateRecord()`), and a decorated service without its own method for an enabled operation. Reading `database`, `http`, `jsonRestApi` or `resource` from `decorateRepository`'s dependencies, `resource` from `decorateService`'s or from the feature's capability, or `trx` in a lifecycle hook throws, naming what replaced it (`repository` and `resources`, `crud`, `options`); spreading those objects leaves the names out. The CRUD service's `view()` refuses `forUpdate`, naming `lock()` inside `withTransaction`.
- `createHooksToCollectChildren` reading through a child repository's `queryAll()` now says which "in" filter the child table must declare for its foreign key when the table refuses the list of owner ids, instead of passing on json-rest-api's validation error.
- **Breaking.** `@jskit-ai/crud-core/server/fieldAccess` and `@jskit-ai/crud-core/server/lookups`, which nothing called since the CRUD runtime was removed, are gone, with the `crud.fieldAccess.writeDenied` message and the `CrudFieldAccess` and `CrudLookupRepository` types.

- **Breaking (data-access redesign).** The JSON:API CRUD runtime is removed, with no alias: `./server/defineCrudJsonApiFeature` (`defineCrudJsonApiFeature`), `./server/resourceRuntime` (`createCrudResourceRuntime`), `./server/jsonApiRepository` (`createCrudJsonApiRepository`), `./server/jsonApiService` (`createCrudJsonApiService`, `repositoryCallOptions`), `./server/createCrudServiceFromResource`, `./server/repositorySupport` and `./server/serviceMethods` (`createCrudServiceRuntime` and the `crudService*Record` helpers). A CRUD feature is `defineCrudFeature({ crud })` on a CRUD contract: its repository is its table's handle, which `decorateRepository` may wrap, and its service the one it builds, which `decorateService` may wrap. The JSON:API repository methods go with it (`queryDocuments`, `queryEveryDocument`, `getDocumentById`, `createDocument`, `createDocuments`, `patchDocumentById`): server code reads and writes through the handle (`query`, `queryAll`, `get`, `create`, `createMany`, `patch`, `lock`). The Before | Now table in the existing-application migration guide maps each one.
- New `./server/defineCrudFeature` exports `defineCrudFeature({ crud, surface, owns?, ownerRepository?, systemScope?, visibility?, permissions?, decorateRepository?, decorateService?, operationLifecycle?, actions?, ... })`: one feature serving a CRUD contract over HTTP and the action catalogue, owning its table (and those in `owns`) through `runtime.resources`. New `./server/crudContracts` exports `CrudContractsProvider`, which provides `crud.contracts`, the registry of the CRUD contracts an application serves, one per namespace and sealed at boot, and `createCrudContracts`. A package with a CRUD feature lists `crud.contracts` in its descriptor's `capabilities.requires`.
- Depends on json-rest-api 2.4.0 (from 2.1.0); see `@jskit-ai/json-rest-api-core`'s CHANGELOG for what it changes.
- A CRUD JSON:API repository's `createDocument` and `patchDocumentById` take `returning: "full"` (the default, unchanged), `"minimal"` (`{ data: { type, id } }`) or `"none"`, so server code that ignores the result skips the read-back: a get through the row policy and lookups, about four queries per written record. `createDocuments(payloads, { trx, context, returning })` creates several records in order in one transaction, all or none, returning `"minimal"` results unless asked for `"full"`.
- The actions of an `internal: true` or `routes: false` CRUD feature are left off the `automation` channel, so the assistant cannot call them, unless their permission names a permission (`require: "all"` or `"any"`), as workspace-scoped CRUD's defaults do. An additional action's own `channels` still decide for it.
- A CRUD JSON:API repository's `queryDocuments(query, options)` throws a `TypeError` naming `queryEveryDocument` when `query.limit` is above the resource's json-rest-api `queryMaxLimit` (100 unless the resource sets it), instead of silently answering only `queryMaxLimit` records. New `queryEveryDocument(query, options)` answers every record the query matches as one JSON:API document `{ data, included }` (each included record once), reading 1,000-record pages in id order in the caller's transaction; its query takes filters, `include` and `fields`, but no `limit`, `cursor` or `sort`. New `queryMaxLimit()` reports the cap. The HTTP and automation list action still caps a larger `limit` and answers one page, whose `meta.pagination` reports the page size, `hasMore` and the next cursor, as before. `@jskit-ai/json-rest-api-core`'s new `queryAllJsonRestCollectionDocument(resource, params, context)` is the every-row read behind it.
- A CRUD JSON:API repository's `getDocumentById(recordId, query, { trx, forUpdate: true })` locks the record's row in `trx` before reading it (`SELECT ... FOR UPDATE`; nothing on SQLite, which runs one transaction at a time), so a concurrent `forUpdate` read or write of it waits until the transaction ends. It used to ignore `forUpdate`. Without a transaction it throws a `TypeError`, as does a `forUpdate` that is not a boolean. The CRUD service's `getDocumentById` passes `forUpdate` through, and the service gains `queryEveryDocument`.

### Upgrading

- json-rest-api 2.4.0 (from 2.1.0): `addResource` now rejects a field type json-rest-schema cannot cast, naming the field (JSKIT's own resources use only castable types); and a write's relationship targets are locked FOR SHARE (LOCK IN SHARE MODE on MySQL), so a lifecycle hook that then updates a referenced parent row in the same transaction should lock that row first, with `getDocumentById(parentId, {}, { trx, forUpdate: true })`, or two such writers can deadlock on the lock upgrade.
- `getDocumentById(..., { forUpdate: true })` now locks: server code that already passes `forUpdate: true` inside its transaction gets the lock it asked for. A call that passes `forUpdate: true` without `trx` now throws; read inside `withTransaction`.
- Give an internal resource explicit `permissions` when the assistant should keep reading it for the users who hold them.
- Server code that calls a CRUD repository's or service's `queryDocuments` with a `limit` above 100 now throws. It already received only 100 records, so a read meant to return more was losing rows. Replace `queryDocuments({ ...filters, limit: N })` and any cursor loop around it with `queryEveryDocument({ ...filters }, options)`, sorting the records it returns in memory; a "too many rows" guard (`rows.length >= N`) then sees the true count. Who is affected:
  - Server code that asked for more than 100 records in a cursor loop around `queryDocuments`.
  - Server code that asked for more than 100 records in one `queryDocuments` call with no cursor: the records past the 100th were dropped, and a "too many rows" guard on that read never fired.
  - Client pages that ask the list routes for 200 or 250 rows are not: they keep working, since HTTP still caps them.
