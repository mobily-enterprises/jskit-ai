# Changelog

## Unreleased

- Three new guide chapters give the JSKIT half of Genesis's identity, quality and data passes (skill references `visual-identity.md`, `quality-pass.md` and `data-pass.md`). [Visual identity](/guide/framework/visual-identity) says where each piece of an identity lives in a JSKIT app: the seed and content colour roles in `src/theme/index.js`, every content colour in `src/theme/palettes.js`, seeded cover art in `src/components/art/`, empty states, the logo and `favicon.svg`, `index.html`'s startup shell and the sign-in `AppBrand.vue`, with the Material 3 pieces it uses (the top app bar, `ShellPrimaryAction`, phone navigation, skeletons, motion tokens, `material-web`'s overlay corners) and its checks. [Quality pass](/guide/framework/quality-pass) says where loading, empty, error and refused states live, how a coded refusal reaches the person through `serverMessage()`, and how to force each state with Playwright. [Data pass](/guide/framework/data-pass) maps each step to its JSKIT pieces (table owners, `expectFlatQueries()` and `countQueries()`, narrowing in the query, constraints tried by server tests, `.cjs` migrations, `indexed: true` and lock indexes) and adds PostgreSQL (concurrent index builds, `NOT VALID` then `VALIDATE`, unindexed foreign keys, partial indexes, `EXPLAIN (ANALYZE, BUFFERS)`) and MySQL (one schema change per migration, `ALGORITHM=INPLACE, LOCK=NONE`, no partial indexes, case-insensitive unique keys, `EXPLAIN ANALYZE`) notes. The JSKIT skill routes each pass to its reference.
- The data-access guide's Layer 4 says how work reads a whole set of rows it decides on (a register's entries) as they stand: every writer of the set locks the row that governs it first, and the work locks that row before its first plain read, after which plain reads are current at any size; work that joins a transaction that may already have read plainly reads the set with `lockPages` (every matching row locked a page at a time, in id order, each page a locking read that sees the latest rows whatever the snapshot), still after the governing lock, since PostgreSQL keeps no new row out of a page already locked; isolation is not the tool. It adds `lockPages` to the handle's table, its index to the MySQL and MariaDB index rule and to the methods that refuse to run outside a transaction, and says `patchWhere` and `deleteWhere` select their rows with a locking read on MySQL and MariaDB. The data-access heuristics point the whole-set case there.
- The data-access guide shows a table its feature counts but never reads back (who took part in an anonymous survey): a `uuid` primary key made with `crypto.randomUUID()`, never a sequence or a time-ordered id, a unique index on the columns that identify a row, and an owning feature whose only API is an insert (`createMany` with `onConflict` ignore, whose rows may now carry their ids) and a count (`aggregate`), with why: a v4 id carries no time or order, MySQL and MariaDB store rows in primary key order, and PostgreSQL's heap shows insertion order to a direct read whatever the key, so no code reading the rows is the protection. Layer 3 says an ignore's rows may carry ids, and a merge's carry none. The data-access heuristics point that case there.
- The data-access guide's Background work section adds work done as one member of a workspace (a record started for the person it is assigned to, a notification for one recipient, a submission synced for the person who made it): `workspaces.memberContext({ workspaceId, userId }, { context: systemContext(reason) })`, resolved and refused as the member's request on a `workspace_user` route is, signed in as them (unlike `{ actorId }`), with request row limits and hidden fields as at their request, and an action run in it naming its surface; never a hand-built context. The Words table defines a member context and the scope bullet names `memberContext` as a source of scope. The data-access and row-policies heuristics and the heuristics index follow.
- The data-access guide's Background work section adds a job whose units are the workspaces themselves, paging them with `workspaces.listForSystem({ afterId, limit }, { context: systemContext(reason) })` (one statement a page, a page shorter than `limit` the last; any other context refused), never the workspaces table, and Tables you don't own points a job that visits every workspace at it. The data-access heuristic and the heuristics index follow.
- The data-access guide says a row policy's `options.trx` names the transaction its read runs in, the one json-rest-api opens for a write whose caller named none included, so an owner API the policy calls with its `options` (a join source, or a handle read such as a role check) joins it and never waits for a second connection.
- The data-access guide's Layer 4 documents `lockWhere`'s `sort` (the order its rows are locked and answered in, then id) and `limit` (only the first rows of that order; `limit: 1` locks one row by a unique key in one statement, as `workspaces.memberships.lockByWorkspaceIdAndUserId` now does), the index MySQL and MariaDB then need, and why a join source takes no lock, not even a shared one (MariaDB has no `FOR SHARE OF`; its `LOCK IN SHARE MODE` covers every row the statement examines), with the owner's shared lock (by a unique key with `limit: 1`) to take first instead. Its row-policy section says a policy may read another owner's rows as stored through that owner's API, which answers a join source under its own `systemScope` narrowed to the call's workspace (a third exception in Background work), and never walks a tree with `withRecursive` (no builder it holds takes one, a walk that starts at the row read does not compile on MariaDB, and one that starts elsewhere reads the reader's whole subtree on every read): a closure table the tree's owner keeps answers it with one `whereExists`. Its Exceptions section says a refused statement points at a missing API, to ask the owner (or JSKIT) for: no rule takes a per-statement exception, and only statements that are data access themselves go in a small file of their own declared as infrastructure.
- The data-access guide's Capability cycles section adds Late requirements: a ring that only a read at call time closes, most often a row policy's, and that cannot or should not be split, is broken with `late: { name: "token" }`, which the kernel resolves once after every feature's boot, so its destination is declared and never depends on what ran before, unlike a setter or a lookup by name; it is read only at call time (in a row policy's `requires`, a request handler, or a method setup builds), never in setup or boot nor destructured in setup, a missing one fails start-up at the end of boot, and the one-way rules still come first. Its row-policy section says a policy receives its feature's late requirements in `requires` too. The typed-features guide adds `late` to the capability terms, to the feature key order (`requires, optional, late, provides`), to the manifest (late capabilities are required), to the formatter's one-property-per-line maps (`jskit/one-property-per-line` now checks a `late` map too), and a Late requirements section beside Optional tokens, with the setup that keeps the capabilities object and the destructuring that fails. The row-policies and typed-features heuristics, and the heuristics index, point a policy's ring and the late requirement errors there.

- The shell and minimal foundation examples approve `@jskit-ai/material-web`'s install script in `allowScripts`, as `jskit update` does for an app: it patches Vuetify's idle loaders (vuetifyjs/vuetify#23393), and a strict install fails on an unapproved script.
- The data-access guide says a row policy narrows with where calls only, since a join inside it is dropped from its where group (JSKIT now throws), and narrows through another table with `whereExists` over `ownTable(name)` or another owner's `joinSource({ alias }, options)`, passing on the `options` the policy is told. Its locks layer adds `lockMode: "share"` for `lock`, `lockMany` and `lockWhere` (also through `workspaces.lock` and `memberships.lockByWorkspaceIdAndUserId`), for read checks only, since share-then-write deadlocks, and why locks stay on owner handles: each owner's rows are locked with its own lock calls in one fixed owner order, never through a join source or a policy. Its Transactions section adds `withTransaction({ ...options, joinOnly: true }, work)` for work that must never open a transaction of its own.
- The UI guide's Browser verification section and the UI testing heuristic find a form field by its exact label (`page.getByLabel("Email", { exact: true })`), since an inexact lookup matches any element whose label contains the text and fails strict mode. The side effects guide says the "Test copy" banner is a note with no label, so `getByLabel("Email")` never finds it.
- New guide chapter, [Side effects and test copies](/guide/framework/side-effects) (skill reference `side-effects.md`): the `SIDE_EFFECTS` contract (`live` acts for real, anything else simulates), what JSKIT simulates, the "Test copy" banner, and a short example for an application's own side effects. The foundations' `AGENTS.md` points to it.
- The application foundations' `bin/develop.js` starts Vite directly under node instead of through `npm run dev`, so stopping the launcher (SIGTERM, as a Preview stop sends) stops Vite too: npm exited on SIGTERM without stopping the script it started, which left Vite serving the port.
- The workspace tenancy guide's Role permissions section says the startup grant check cannot see a permission the application checks in its own code, so before removing or renaming a reported grant an agent searches the code for it (`hasPermission()`, `can()`, permission string checks, including names built in code such as `` `crud.${resource}.list` ``), lists one the application checks in `roleCatalog.customPermissions`, and removes the grant only when nothing uses it. The generated guide, skill reference and workspace-server pattern copies follow.
