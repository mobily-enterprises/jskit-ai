# Changelog

## Unreleased

- `expectFlatQueries` fails when the path sent no statement at any size. That is a test counting on a channel the path does not use, such as no `knex` in a test whose features run on one and that booted no server, which measured 0 at every size and passed.
- A call's settings stay on that call. `withTransaction` hands its work only `{ context, trx }`, and so does a handle to its `afterWrite` hooks, to `lockOrCreate`'s work and to its own nested calls, instead of every option the caller passed: an outer `returning: "none"` made a create inside, or `findOrCreate`, answer nothing, and an outer `missing: "skip"` made a get inside answer null for a missing record. A handle's own write and read still take its `format`. `passedOn(options)`, exported from `./server`, gives the same `{ context, trx }` to code that calls another table.
- A row policy (an owner's or a contribution) is told who the call runs for only as `caller`: json-rest-api's own `system` flag is no longer handed on beside it, so a policy has one way to tell a system context, a job, a user and no one apart. No JSKIT policy read the flag.
- `expectScoped` compares the path's answers: it seeds owner A and runs the path as A, then seeds owner B and runs it as A again, and fails when the second answer differs from the first, as well as when the path changed or removed a row of B's. It used to fail only when the answer held one of B's rows by id with the same fields, so a report that joined, summed or counted B's rows (an answer like "Pat at business B") passed. The path runs twice, so a write answers what repeats. B's rows are read back by id, a thousand per read, and the tables' ids in one statement each, instead of whole tables through `queryAll`, which refused a table past its row limit.
- A handle's plain read answers the hidden fields (`hidden: true`) its `fields` names: `get`, `query` and `queryAll` in their params, and `lock`, `lockMany`, `lockWhere` and `claim` in their options. json-rest-api never selects a hidden field, so the handle reads them in one more statement per 1,000 records, on the table as `scopedQuery` gives it (the caller's ownership and the row policy applied), in the call's transaction, and answers them as json-rest-api reads their type. A hidden field may be an id, string, integer, number or boolean; naming one of any other type refuses the read before it runs. A read without `fields`, and any JSON:API read (`format: "jsonapi"`), still never answers one. Before, an owner read its own bearer token or storage key with a `scopedQuery` report, and a job that had to learn each row's owner across workspaces had to unhide the ownership field.
- `withoutHiddenFields(repository, resource)` (`@jskit-ai/resource-runtime/server`) answers the repository an owner gives other features: the same, except that a read whose `fields` names a hidden field of the resource is refused, with a TypeError naming the method and fields, unless it runs in a system context or one it derived. A resource without hidden fields keeps its repository as it is.
- **Breaking.** A query field's `select` (an `owns` entry's `queryFields`) receives `{ raw, column, filters }` instead of json-rest-api's `{ knex, db, column, context, ... }`. `raw(sql, bindings)` builds one SQL expression from a string and its bindings as an array, and is a value only: awaiting it, or running it as a statement, throws. `column(field)` names a field's column, and `filters` is the read's filters, frozen. A select could run any statement on the Knex it was handed, with no ownership scope; now it writes the field's value and nothing else: `select({ raw, column }) { return raw("?? - coalesce(??, 0)", [column("receivedWeight"), column("processedWeight")]); }`. A handle's `raw()` refuses the same way bindings that are not an array, or a third argument. jskit/sql-literal holds a destructured `raw(...)` to the rules it holds `handle.raw(...)` to (one literal, bindings for its placeholders, no statement words).
- `lockWhere` and `claim` take `fields` in their options, as `lock` and `lockMany` do (`{ ...txOptions, fields: ["stage"] }`), and read only those, so a belongs-to field left out costs no check that its related record is visible: a claim of a job that links to two tables was a locking read and two checks, and is the locking read alone. Without `fields` they read what `lockMany` reads, so a collection with `hydrateOnView: false` is no longer loaded unless `fields` names it.
- A handle write refuses a condition its options name with no value: `patch` with `lockVersion: undefined` or `onlyIf: undefined`, and `patchMany` or `patchWhere` with `onlyIf: undefined`, throw a TypeError naming the resource, the method and the key (`notes.patch() options.lockVersion is undefined`). They used to run without the condition, so a version read under the wrong field name made a version advance only read. A call without the condition leaves the key out.
- An error a transaction's work throws itself reaches the caller of `withTransaction` (or of a handle call that opened its own transaction) reporting `transactionOutcome: "rolledBack"`, not enumerable, with its status and code unchanged, so `isLostDuplicateInsertRace` and a caller's retry tell a rolled-back duplicate the work turned into its own 409 from one inside a joined transaction. A frozen error is rethrown as it is.
- A handle's `query`, `queryAll` and `aggregate` whose filters give an empty list to a list filter (the id filter, or a filter with `filterOperator: "in"`) answer without a statement what a read matching no row answers: no records (`hasMore: false`), and for `aggregate` no groups, or one row of totals whose counts are 0 and other measures null. The context, page size and filter guards still run first; a JSON:API (`format: "jsonapi"`) query still reads.
- **Security.** `createStandaloneResources` refuses, on the Knex client of a JSKIT server, a table one of the server's features owns, saying which: standalone resources (for a command-line script) built a runtime of their own, with its own table owners and any system scope, so code inside a server could own an app table a second time and read it past its owner. A second Knex client on the same database is not recognised; code inside a server uses its features' handles.
- A job context from `forWorkspace`, `forUser` or `forWorkspaceUser` carries the event scope of its workspace, user or both (`{ kind: "workspace", id }`, `{ kind: "user", id }`, `{ kind: "workspace_user", id, scopeId, userId }`, as a request there does), so an action event it publishes reaches that audience, where it was scoped global.
- **Security.** A context that names no workspace or no user is refused wherever a table owned by it is read, not only on that table's own handle: an `include`, a link's visibility check and a link write into a workspace- or user-owned table now fail with json-rest-api's `REST_API_AUTOFILTER_CONTEXT`, where they read or linked the rows whose owner is NULL. The workspace and user owner resolvers answer nothing (undefined) when the context names no owner; only `workspace_or_shared` keeps its own resolver, which answers null, so a context with no workspace still reads only the shared rows.
- `own()` refuses at startup a cross-table filter (a `searchSchema` or field `search` entry whose `actualField` or `oneOf` names "resource.field") whose target field is not declared `indexed: true`, naming the filter, the target and the fix. json-rest-api refuses that filter only at the first query that uses it. A filter whose target table no feature owns yet is checked when its owner owns it.
- Runs on json-rest-api 3.0.0's release candidate (a17b722). A record written back as it was read keeps a link to a target the writer cannot see: the null it read counts as unchanged, while linking or clearing a visible target applies. A read that includes a link's target no longer checks that link's visibility again (one statement fewer per included type). A system context may group by and count distinct a hidden ownership field, so a job finds its units through its handle; a request is still refused. Stored integer and number values over BIGINT columns read as numbers when exact; ids stay strings, and getter, computed and virtual fields keep their own values.
- A system context's `forWorkspace`, `forUser` and `forWorkspaceUser` take `{ actorId }` last, for work a job does for one person (a request it carries out later). The derived context carries it as `onBehalfOf`, which audit fields read with the kernel's `resolveAuditActorId(context)`, and a row policy sees it as `caller.actorId` beside `kind: "job"`. It is attribution only: it never changes which rows the job reaches, and it signs no one in, so `resolveActorId`, `requireAuth` and an action's `authenticated` permission still see no one. Any other last argument is refused.
- `@jskit-ai/resource-runtime/test` exports `startTestFeatures({ knex, features, requires, inputs, createTables, logger })`: it starts features and providers as an application's server does, without HTTP, on a test resource runtime over the test's Knex, with the kernel's events and actions. The kernel orders them by their requires, each owner gets its handles and system context, every boot runs (so `crud.contracts` is sealed), and it answers `{ capabilities, resources, stop }`, where `capabilities` holds what `requires` names.
- `patch(id, changes, { ...options, onlyIf })` compares a `hidden` field: the UPDATE compares the onlyIf values itself, after the lock that tells a missing record from a changed one, where the handle compared them with the locked record, which no read gives a hidden field, so such a patch never applied unless it also said `missing: "skip"`.
- A row policy (and each contribution) receives `caller`, who the call runs for: `{ kind: "system", reason }` for a system context, `{ kind: "job", reason }` for a context `forWorkspace`, `forUser` or `forWorkspaceUser` derived from one, `{ kind: "user", userId }` for a signed-in request and `{ kind: "anonymous" }` otherwise. A derived job context names no user, so a policy that keyed on the actor treated it as an anonymous request; it now tells them apart by `caller.kind`. `system` is still passed.
- A table whose primary key is a `uuid` or a `string` takes its ids as text without a `normalizeId` on its `owns` entry; json-rest-api's default normalizer takes numeric ids only and answered "Resource document id is invalid". An owner's own `normalizeId` still wins.
- `createMany` with `onConflict: { action: "merge" }` and no `merge` list works on a table that stores `createdAt`: the merge list the handle builds from the rows' fields leaves out the conflict keys, the ownership fields and the lock version, which json-rest-api refused to merge ("onConflict.merge cannot change …"), as well as the id and `createdAt`.
- `aggregate` counts `id` (`{ count: "id" }` or `{ countDistinct: "id" }`) as the count of rows, on a schema that declares no id field too; json-rest-api refused it as an unknown field.
- A handle's included records read as a read of their own resource answers them, at every depth and in an included collection: a belongs-to field carries its id under its own key (`pet.contactId`) and the related record stays nested only when the include names it (`include: "pet.contact"`), where an included record kept json-rest-api's shape (`pet.contact: { id }`, no `contactId`). An included record leaves out a collection it does not include itself, which json-rest-api does not read for it and would answer as empty.
- `lock` and `lockMany` take `fields` in their options (`{ ...txOptions, fields: ["stage"] }`) and read only those, so a belongs-to field left out costs no check that its related record is visible: a lock of a record with two relations was a locking read and two checks, and is the locking read alone. A `patch` with `lockVersion` or `onlyIf` locks only the fields it compares, so its own locking read checks no relation, and `onlyIf` may now compare a field reads hide by default (it never matched before).
- A sparse `fields` names a belongs-to field by its own key (`customerId`) as well as by its relationship (`customer`): the key used to select no relationship and answer `customerId: null` for every row. A sparse read leaves out a belongs-to field it does not name, where it answered `null`.
- A collection relation with `hydrateOnList: false` (lists: `query`, `queryAll`) or `hydrateOnView: false` (`get`, `lock`, `lockMany`) no longer loads its rows on that kind of read unless the read includes it or names it in `fields`, as the CRUD runtime before the redesign did.
- On a table with a lock version, a patch that changes no field still advances the version, and now stamps `updatedAt` as every other update does: `patch(id, {}, { lockVersion })` (which did not stamp before) and an empty `patchMany` row, so many records advance in one UPDATE (`patchMany(ids.map((id) => ({ id })), options)`). A table without a lock version still writes nothing for an empty change.
- **Breaking.** Every handle owns the `id` filter, which takes one id or a list (`filters: { id }`), and registering a table resource that declares its own refuses: a `searchSchema` `id` entry (shared or the owner's) or `search: true` on the `id` field. A declared scalar `id` entry used to replace the handle's, so `filters: { id: ids }` failed on that table. **Upgrading:** delete the resource's `id: { type: "id", actualField: "id" }` search entry and any `search: true` on its `id` field; filters by one id or a list keep working.
- **Breaking (security).** A system context comes only from a declared system scope. `runtime.resources` no longer has `createSystemContext`: `declareSystemScope(featureId, systemScope)` records the scope (one per feature; declaring another throws) and answers the feature's `systemContext(reason)` factory, which the kernel hands a feature's setup, and `systemScopes()` lists them. `createResourceRuntime` and the `./server/resourceHost` subpath are no longer exported, so no code outside the package builds a runtime or a host of its own: code outside a JSKIT server owns its tables with `createStandaloneResources({ knex, feature, owns, systemScope? })`, which answers `{ resources, systemContext? }`, and tests with `createTestResourceRuntime` from `./test`, which now takes `hostHooks` for json-rest-api hooks a test installs. `buildJsonRestQueryParams`, `resolveWorkspaceScopeValue` and `resolveUserScopeValue` are exported from `./server`. `resolveUserScopeValue` throws when a context's `scopeValues.userId` and `visibilityContext.userId` name two users, as the workspace resolver does for two workspaces, instead of the scope value winning.
- A table resource whose schema stores `createdAt` and `updatedAt` as date-times has every handle write stamp them: `create` and `createMany` stamp both, `patch`, `patchMany`, `patchWhere` and an upsert merge stamp `updatedAt` (a merge keeps the stored `createdAt` of a record it updates), and a patch that changes nothing stamps nothing. The stamps replace what the caller sends, so a request can never forge them; only a system context, or a context it derived (an import, a migration, a seed), sets its own, and a timestamp it leaves out is stamped. A call without a context, which server code may make on a public table, is a request's: server code cannot pass a forged body through, and a feature that writes its own timestamps declares a `systemScope` and writes in its system context. Only the CRUD service stamped them before, so server code that wrote through a handle left them unchanged.
- Handles gain `lockOrCreate(row, options, work)`: on a table with no owners it locks the record with `row.id`, creating it from `row` first when it is missing (an insert that ignores a clash on the id), and runs `work(record, txOptions)` in that transaction, so work that fails leaves no record behind. In the caller's transaction it runs there once; on its own it opens a transaction that runs work once, and when two first uses of one id collide on the insert (a deadlock, or a duplicate key) before work starts, the loser runs again, up to four runs in all.
- **Breaking: the package is now `@jskit-ai/resource-runtime`** (was `@jskit-ai/json-rest-api-core`), on json-rest-api 3.0.0. Its provider is `ResourceRuntimeProvider`, which provides `runtime.resources`; the host it builds is `createResourceHost` (was `createJsonRestApiHost`), at `./server/resourceHost` (was `./server/jsonRestApiHost`). The `runtime.json-rest-api` capability and the host helpers `addResourceIfMissing`, `createJsonRestResourceScopeOptions`, `queryAllJsonRestCollectionRows`, `queryAllJsonRestCollectionDocument` and `extractJsonRestCollectionRows` are removed: a feature owns its tables with `defineFeature({ owns })` and reads every matching row with its handle's `queryAll`.
- **`runtime.resources`.** The kernel calls `own(featureId, owns)` for a feature with `owns`: it registers each table resource (or `{ resource, rowPolicy, hooks: { afterWrite }, acceptsContributions, normalizeId, queryFields, searchSchema }`) under its name, throws `DuplicateOwnerError` when another feature owns the table or the name, and answers one handle per resource. `createSystemContext({ feature, systemScope, reason })` answers json-rest-api's system context, with `forWorkspace(id)` and `forUser(id)` for work scoped to one workspace or user.
- **Handles.** Every method takes `options = { context, trx }` last and refuses an owned resource's call without a context (`MissingScopeError`). Reads: `query(params)` answers `{ records, page: { size, hasMore, next } }` and requires `page.size` (`UnpagedQueryError`) no larger than the resource's page limit (`PageSizeError`), with `page.after` (the previous page's `next`) for scrolling or `page.number` (from 1) for a numbered page, each one statement with no count; `queryAll` reads in 1,000-row pages and, in a request context, throws `RowLimitError` past 10,000 rows (a 400 coded `RESOURCE_ROW_LIMIT`, with the message code `resource.rowLimit` for the user's language) (system, workspace and user job contexts have no limit); `get(id, params, options)` answers a record; `aggregate` answers rows. Writes: `create`, `patch` (answers the record; `lockVersion` throws `StaleRecordError`, 409 `crud.document.lockVersionConflict`; `onlyIf` patches only matching rows and answers null otherwise) and `delete` (answers the id), and the many-row `createMany`, `patchMany`, `patchWhere` and `deleteWhere`, one statement per chunk. One missing-row rule: `get`, `patch`, `delete` and `lock` throw json-rest-api's not-found error (404) for a missing or hidden row, and answer null with `missing: "skip"`, which never fails the caller's transaction. Every filter takes `id`, one id or a list, so `patchWhere({ id: ids }, changes)` and `deleteWhere({ id: ids })` cover a list of ids. An upsert's rows carry no id, and `patchWhere` and `deleteWhere` with empty filters need `all: true`. Locks: `lock`, `lockMany`, `lockWhere`, `claim({ filters, sort, take }, options)`. Escape hatch: `scopedQuery` answers `{ query }`, a read-only builder with ownership and the row policy applied, with `column` and `raw`. Reads take `(params, options)` and writes `(data, options)`; settings ride in options, as `{ ...options, lockVersion }`. `withTransaction(options, work)` runs work in the caller's transaction or one it opens and retries a deadlock victim unless `{ ...options, retry: false }`; `{ ...options, outermost: true }` refuses a call inside a transaction. When work throws, the caller gets its own error; a failed write inside it or a failed commit arrives as json-rest-api's `RestApiWriteError` with the transaction's outcome. `findOrCreate({ id, ...attributes }, options)` reads the record with that id or creates it, and answers the winner's record when a concurrent creation wins outside a transaction. An id another scope's row holds answers a missing record, as `get` of it does, never `null` or that row, so it tells the caller no more than any id it cannot see. `afterWrite` hooks run once per write in its transaction and scope.
- A system context also derives `forWorkspaceUser(workspaceId, userId)`: one user's context inside one workspace, so a `workspace_user` table reads that user's rows in that workspace, a `workspace` table the workspace's and a `user` table the user's. Both ids are required.
- **Row policies** receive `ownTable(name)`, a SELECT-only builder over the owner's own tables, and a resource whose owner says `acceptsContributions` takes other features' `contributeRowPolicy(name, policy)`: each contribution is ANDed with the owner's policy inside its own group, so it only narrows.
- **`workspace_or_shared`** ownership reads a workspace's rows and the rows whose workspace is null, and writes only its own.
- **`./test`:** `expectScoped`, `expectFlatQueries` (moved from database-runtime; it now allows the later chunks a many-row write reports), `expectEveryTableOwned`, `requireTestDatabase` and `createTestResourceRuntime`.
- json-rest-api 3.0.0 includes 2.2.0 to 2.4.0. A handle's `queryAll` reads in 1,000-row pages; writes skip the post-write refresh nothing observes (a created child: 9 statements and 5 policy runs instead of 11 and 7); linkage checks run one query per type; reads copy records for `originalRecord` only for hooks that can read it (a query of 100 rows of 38 KB: about a third of the CPU). Also from 2.2.0-2.3.1: `aggregate()`, `email` and `uuid` field types, `retired: true` fields, AnyAPI indexed slots, and relationship targets locked FOR SHARE instead of FOR UPDATE.
