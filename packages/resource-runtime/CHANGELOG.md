# Changelog

## Unreleased

- Depends on json-rest-api 3.1.4 exactly (from 3.1.3), from the registry with its published integrity: a patch, put or patchMany that stores the values a row already holds answers the row as stored on MySQL and MariaDB (it answered the values this transaction first read), and AnyAPI storage checks its tables' columns with one statement at start-up.
- A paged `aggregate()` (`page: { size, number }`) answers `{ rows, page: { size, number, hasMore, next } }`, as `query()` answers a page, instead of a bare array a caller could take for every group; read the next page while `page.hasMore`. An unpaged grouped aggregate still answers every group or throws `GroupLimitError`, whose message now says to read pages. Upgrading: a caller passing `page` reads the groups from `.rows`.
- Depends on json-rest-api 3.1.3 exactly (from 3.1.2), from the registry with its published integrity: a write checks each linked target type with one read of the targets' ids (their minimal records only for a target resource with a `checkPermissions` hook), which also takes the shared lock on the belongs-to and polymorphic targets it stores, before `beforeSchemaValidate` rather than after the `beforeDataCall` hooks; in a system context a belongs-to its declared foreign key protects is left to that key, so a missing target there fails with the database's foreign key error instead of `not_found`. json-rest-api now asks for json-rest-schema ^1.0.20.
- Depends on json-rest-api 3.1.2 exactly (from 3.1.1), from the registry with its published integrity: json-rest-api bounds a blob field itself too (`maxBytes` required, a blob answered only where `fields` names it, at most 16 MiB of named blobs per read, none in an include, `queryAll` or HTTP response, many-row write statements chunked by blob bytes, and the MySQL/MariaDB column type chosen by `maxBytes`), its `contains`, `startsWith` and `endsWith` filters match `%`, `_` and `\` literally on every database, a relationship write checks and locks each related type's targets in one query, and an AnyAPI many-to-many read costs its own link rows instead of growing with the square of them.
- A search filter of an `owns` entry may read other owners' tables through their join sources: `joinSources: { alias: ({ requires, owned }) => owner }` names, by alias, the owner answering each (an owner API the feature requires, or one of its own handles), and its `applyFilter(query, value, { column, joinSource })` gets `joinSource(alias)`, that owner's `{ query, column }` for the caller's scope (its ownership, its row policy, never a hidden column), for a `whereExists` or `whereNotExists` tied to the row with `whereColumn`. A handle builds the join sources a read's filters use before the read, in the call's own context and transaction, so a handle's `query`, `queryAll`, `queryPages`, `aggregate` and `joinSource` take such a filter in one statement, on SQLite, PostgreSQL and MariaDB. A search for the rows that have, or lack, a related owner's rows no longer resolves that owner's ids first or keeps a raw-SQL exception. `own()` refuses at startup a `joinSources` that is not a record of functions under valid aliases, and such a filter with `oneOf` or without `applyFilter`; a read throws naming the filter when its picker answers no owner with `joinSource`. On MySQL and MariaDB `patchWhere`, `deleteWhere`, `lockWhere` and `claim` refuse such a filter as json-rest-api refuses a filter on another table's field (`RestApiValidationError`, rule `selection_cross_table`, the cause of a write's `RestApiWriteError`), since those databases read another table from the transaction's snapshot without locking it, as json-rest-api refuses a filter on another table's field; PostgreSQL and SQLite take it. The data-access guide's Layer 5 shows the filter and how an app switches a report or a pre-resolved id list to it.
- `lock`, `lockMany`, `lockWhere` and `claim` take `include` again, for belongs-to relationships: after the lock's own rows, the records they name are locked through each related table's own handle (its scope, its row policy, its hidden fields), in id order, with the call's lock mode, each included table once however many rows name it, and nested as a read's include nests them, `include: "batch.yard"` locking the yards after the batches. On MySQL and MariaDB the links are read with a locking read of the rows the lock holds, so a record committed after the transaction's first plain read is found and locked, which a plain read after the lock misses (`lockedReads.mysql.test.js`). A link to a record the caller may not see reads as in a read: its belongs-to field null, the relationship undefined. A collection, or a name that is no belongs-to relationship, is still a TypeError before any statement, now saying to lock a collection's rows with that table's own `lockWhere()`; `claim` refuses `include` named both in its params and its options. Upgrading: none; a read after the lock that only fetched the locked rows' parents may become the lock's `include`.
- `queryAll({ ..., take })` answers the first `take` records the filters match, in id order or `sort`, and reads no row past them: pages of `pageLimits().server` rows, the last no larger than the rows still wanted, each later page reported as `queryPages` reports its own so `expectFlatQueries()` allows it. `take` is the read's bound, so a request may name more than the request row limit (10,000 by default) and never gets `RowLimitError`; without it a request still stops at that limit. `take` is a whole number from 1, or a TypeError before any statement; `take: undefined` is no take. A request that needed the first N rows past the limit, or read every row only to keep the first few, names `take`.
- **Breaking.** A blob field (`type: "blob"` with `maxBytes`) is checked and bounded, on SQLite, PostgreSQL and MariaDB. Every write (`create`, `findOrCreate`, `createMany`, `patch`, `patchMany`, `patchWhere`, `lockOrCreate`, upserts) checks its blob values first, before any statement (a transaction's BEGIN for an `afterWrite` hook, or the row lock of a `lockVersion` or `onlyIf` patch, included): a Buffer or a Uint8Array (stored as a Buffer) of at most `maxBytes`, or null; anything else is a `RestApiValidationError` on the field (rule `blob` or `max_bytes`, a 422). Every read leaves a blob out unless its `fields` names it, answers it as a Buffer and holds at most 16 MiB of the blobs it names, or one record's: `get` and `lock` read one record's, a `query` page and `lockMany`'s ids are refused past the records whose `maxBytes` fit 16 MiB, each `queryPages` page holds no more, and `queryAll`, `lockWhere` and `claim`, which read every matching row at once, refuse to name one. No read names an included table's blob, since an include holds any number of records, and `joinSource()` carries no blob column, so a report's `select("k.*")` reads none. A JSON:API `query` or `get` whose sparse fieldset names a blob is a 400 (`JSON_API_FIELDSET_INVALID`, message code `resource.blobFields`), since JSON holds no binary. Before, a blob was any value of any size, read by every list. Upgrading: a read that needs a blob names it, `get(id, { fields: ["image"] }, options)`, since `get` without `fields` no longer answers it; a read of every row that answered blobs reads them a page at a time with `queryPages`, or a record's with `get`; a page of blobs asks for no more records than fit 16 MiB; an included record's blob is read through its own table's handle; a JSON:API client leaves blobs out of its sparse fieldsets, and a route of its own serves one as the response body.
- A report over two owners' rows, asking which of its rows have or lack the other owner's rows (`whereExists`, `whereNotExists` over that owner's `joinSource()`, tied with `whereColumn`) or counting them (a grouped join source joined in), is tested in one statement on SQLite, PostgreSQL and MariaDB, the other owner's ownership and row policy deciding which of its rows count. The data-access guide's Layer 5 shows it, and points rows matched by a related row's value to a cross-table search filter in a plain read.
- **Breaking.** A search filter that reads another owner's table is tested, on SQLite, PostgreSQL and MariaDB, to match only the rows the caller's scope reads there: json-rest-api joins the table as its own read, so its ownership, its owner's row policy and the policies contributed to it apply, in `query`, `queryAll` and `aggregate`, each row once through a has-many path too. `own()` refuses, at startup and naming the filter, one that reads a `system` table from a table that is not `system` (a request would have read it, since only the handle asks for a system context) and one on a field the other table hides (it would tell a caller which rows hold a value it may not read); the message says to filter by the ids the other owner answers instead. Upgrading: a filter onto a `system` table becomes a filter on the table's own fields, or on the ids that table's owner answers through its owner API; a filter onto a hidden field filters on a field the other table shows.
- **Breaking.** A grouped `aggregate` never answers part of its groups. Without `page` it asked json-rest-api for its default page (20 groups) and dropped the `hasMore` that said more were left, so a total per user, per month or per workspace silently lost every group past the 20th. It now asks for the most one statement answers, `pageLimits().request` (the resource's `queryMaxLimit`), and throws `GroupLimitError` (a 400 coded `RESOURCE_GROUP_LIMIT`, message code `resource.groupLimit`) when there are more. `page: { size, number }` reads them in pages, a page shorter than `size` being the last; a `page` without `size` is a TypeError. Upgrading: a grouped aggregate that can have more groups than `queryMaxLimit` reads them in pages, `page: { size, number }`, until a page answers fewer than `size`; one that passed `page` without `size` names it.
- `queryPages(params, options)` reads what `queryAll` reads a page at a time, `for await (const records of handle.queryPages(params, options))`, so a job over a table of any size holds one page in memory. Each page is one statement of up to `pageLimits().server` rows, plus the reads of its includes and of the hidden fields it names, and starts after the sort values of the page before: a job may change what its filters match as it goes, and no row still to come is skipped or read twice while it leaves the sort fields' values (the id, by default) alone. In a request it throws `RowLimitError` at the request row limit, as `queryAll` does, before answering the page that passes it. `expectFlatQueries()` allows each later page's own statements, which the handle reports as a many-row write reports its later chunks, so a paged read measures flat however few rows its pages hold. `withoutHiddenFields` strips hidden fields from each page it hands another feature, and refuses a hidden field its fields name, from `queryPages` or an owner's method of any other name, as a rejected promise that is also pages that throw, so `await` and `for await` both get the refusal and none is left unhandled; another async iterable it answers, such as a Node stream, passes as it is. `pageLimits()` also answers `requestRows`, the request row limit, and `RowLimitError` names the call that hit it and points to `queryPages`.
- A test pins how `startTestFeatures` meets a capability cycle between two table owners, one of them through an `optional` require: it refuses them before any setup with the kernel's `Provider capability cycle detected: children -> parents -> children.`, as the server's boot does. The data-access guide says what such a cycle is, how it shows up and how to keep requires pointing one way.
- **Breaking.** `lock`, `lockMany`, `lockWhere` and `claim` refuse `include` (in their options, or in `claim`'s params; `include: []` too) with a TypeError before any statement, saying how to read the related records: they read no included records and dropped it silently, so a caller got its locked rows without their relations and no word. The related records come from a read after the lock in the same transaction; on MySQL and MariaDB that read is current only when the lock came before the transaction's first plain read, which `lockedReads.mysql.test.js` shows with two transactions on one seat. Upgrading: drop `include` from the lock, and read the related records after it in the same transaction, `queryAll({ filters: { id: ids }, include }, txOptions)` or the related table's read by id list.
- An `owns` entry's `rowPolicy` receives the owning feature's dependencies (the capabilities it requires, and its optional ones), by local name, as `requires`, the same values its setup receives, beside `caller` and `ownTable`. `own(featureId, owns, { requires })` takes them, and defineFeature passes them; a policy needing another feature's capability had no way to reach it. A contributed row policy is unchanged: its feature builds it in setup, with its own.
- **Breaking.** A many-row call (`createMany`, `patchMany`, `patchWhere`, `deleteWhere`) refuses a `chunkSize` that is not a whole number of at least 100 rows, with a `TypeError` naming the call, before any statement; one left out is still 500. A chunk of 1 or 5 rows sent a statement every row or few, as a loop of single-row writes does, and `expectFlatQueries()` allowed those statements as the call's later chunks, so it passed a write that grew with its rows. Upgrading: a call that passed a smaller `chunkSize` passes 100 or more, or none.
- `expectFlatQueries()` counts only the measured path's own statements and many-row reports, from `run` and the async work it starts: a test or a background loop running beside it in the same process no longer changes the count. The many-row channel is process-wide, so another test's chunked write was taken for the path's own later chunks, which could hide statements that grow with the rows.
- The resource runtime answers `tableResource(name)`: the table resource a feature owns under that name, or null. The CRUD contracts registry checks at boot, through it, what each contract's includes list of the tables they include.
- The MariaDB many-row race tests read `INNODB_TRX` every 150 ms, where they polled it every 25 ms: InnoDB refreshes its copy of that table only when nothing has read it for 0.1 s, so the tests read the copy from before the writers reached the row's lock until their 10 s bound ran out, on any server whose test user may read it (CI's root).
- Depends on json-rest-api 3.1.1 exactly (from 3.1.0), from the registry with its published integrity: a sort on the ID, or on a required attribute stored in its own table, carries no null placement, so PostgreSQL and MariaDB read a descending page from an index instead of sorting every matching row.
- A handle's `joinSource()` carries the table's ownership fields (`workspaceId`, `userId`) as join keys, hidden or not, and `column()` names them: a report joining another owner's scoped rows on the workspace, such as a system job reading each workspace's settings beside its bookings, was refused (`contactRoles.joinSource() carries no hidden field, so it has no column for "workspaceId"`). They name the caller's own scope, so nothing secret leaves the owner; every other hidden column stays out, and `column()` still refuses it.
- Depends on json-rest-api 3.1.0 exactly (from 3.0.1), from the registry with its published integrity: `lockMode: "noKeyUpdate"`, ON CONFLICT on the matching unique index's exact columns, the PostgreSQL merge race on an uncommitted insert, and the `xid8` field type the change horizon reads.
- Tests pin three paths the guide now documents: a shared row of a `workspace_or_shared` table is written in the owner's root system context, naming `workspaceId: null`, also inside a request's transaction, and never from a request or a derived job context (`forUser` is refused 403); a job's `actorId` never moves its scope, while a row policy may hold a job done for a person to that person's rows; and a hand route's `request.callOptions()` scopes user, workspace and workspace_user tables as the same request's action does, with no user scope when no one is signed in.
- A table resource reads an xid8 change stamp through an `xid8` field, json-rest-api 3.1.0's type for PostgreSQL's transaction id: decimal text below 2^64, which filters such as `changedSince: { type: "xid8", actualField: "changed", filterOperator: ">=" }` compare as transaction ids in SQL. A malformed cursor is refused as `REST_API_VALIDATION` before any statement, where a string field sent it to PostgreSQL (22P02), and the field is refused at registration on MySQL, MariaDB and SQLite. With `changeHorizon()`, a read of what changed since goes through the handle, where it was a hand-written scoped query; the data-access guide's "What changed since" gives the migration (an xid8 column a trigger stamps on every insert and update), the field, the filters and the read.
- Every handle has `changeHorizon(options)`: PostgreSQL's snapshot horizon, `pg_snapshot_xmin(pg_current_snapshot())`, as decimal text, read in the caller's transaction when there is one, with the call's context checked as for every call. Every transaction below it had finished when it was read, so a read of what changed starts there: a later read of the rows whose xid8 change stamp is at or above it finds what an open transaction wrote, a row whose id was taken before its transaction committed and a changed older row included, which "past the highest id seen" misses. It reads no row, where it was a hand-written `knex.raw` beside the handle. MySQL, MariaDB and SQLite stamp no row with its transaction: there it throws `UnsupportedDatabaseError` (code `RESOURCE_DATABASE_UNSUPPORTED`, exported from `./server`) before any statement. `changes.postgres.test.js` proves the catch-up with a writer still open at the horizon.
- **Security.** A table resource with ownership `system` (rows of no workspace or user, such as an agent's runs or a server's leases) answers only a system context. Every call with a request's context, a job context derived with `forWorkspace`, `forUser` or `forWorkspaceUser`, or none throws `SystemContextRequiredError` (code `RESOURCE_SYSTEM_CONTEXT_REQUIRED`, exported from `./server`) before any statement: such a table has no ownership predicate, so that context reached every workspace's rows. The table gets no autofilter preset; the owner's own methods decide what a request may see.
- `lock`, `lockMany`, `lockWhere`, `claim`, `lockOrCreate` and `patchWhere` take `lockMode: "update"` (the default, `FOR UPDATE`) or `"noKeyUpdate"`, passed on to json-rest-api: on PostgreSQL `FOR NO KEY UPDATE`, which still keeps every other lock and write of the row out but lets another transaction insert a row that references it; MySQL, MariaDB and SQLite lock as for `"update"`. Another value throws a TypeError naming the resource and the method before anything runs (`notes.lock() lockMode is "update" (the default) or "noKeyUpdate". Received: "share"`).
- `./test` re-exports database-runtime's `createPackageTestKnex(t, { environment })`. The package's own data tests run on it, so a `DB_CLIENT=pg` run proves their paths on PostgreSQL, each test in a schema of its own; `locks.postgres.test.js` adds PostgreSQL's concurrent cases with real transactions: two `patchWhere` calls racing for one row, `deleteWhere` against `patchWhere`, a `patchWhere` that waited writing only rows that still match, two `claim` workers taking different rows, `lockMany` and `lockWhere` waiting for a holder, upserts of one key behind an uncommitted insert, a deadlock victim running again, `retryLostInsertRace`, `findOrCreate` and `lockOrCreate` first uses at once, and `lockMode: "noKeyUpdate"`. CI runs them, and the data tests of this package and crud-core, on PostgreSQL 17.
- Tests pin how a whole number stored in a BIGINT column that is not an id (a counter, a read position) reads through a handle, on MariaDB/MySQL and PostgreSQL (`storedIntegers.mysql.test.js` and `storedIntegers.postgres.test.js`, the latter in CI's PostgreSQL job). Both drivers read BIGINT as text, and a field of type `integer` answers a number on create, get, query, queryAll, patch, createMany, patchMany, lockMany, claim, aggregate and a hidden-field read, while an id field answers text. Past 2^53 − 1 the digits stay text, never a rounded number, and a `scopedQuery` row is the driver's text. No behaviour changes.
- `./server` exports `checkForeignKeys({ knex, resources, tables })`, which compares the table resources' declared `foreignKeys` (each field mapped to its column as json-rest-api stores it) with the keys the database holds: `missing` lists a declared key the database lacks, `undeclared` a key of one of `tables` that nothing declares. `jskit test --databases` runs it once per run on the prepared test database; it never runs at boot. A declared `foreignKeys` reaches the json-rest-api resource unchanged; json-rest-api 3.0.1 only keeps it for its table helpers.
- **Security.** A handle answers `joinSource({ alias, filters }, options)`: `{ query, column }`, the caller's scoped rows under the alias (ownership, the row policy and the filters applied) with the stored columns a read answers, never a hidden one, and `column(field)`, which refuses a hidden field. `withoutHiddenFields` hands another feature no other query builder: a method answering one, at once or inside its answer, is refused outside a system context with a TypeError naming the method and pointing at `joinSource`. A join source an owner built on `scopedQuery()` selected every column, so `source.query.select(source.column("publicToken"))` read another feature's hidden values; such a source becomes the handle's `joinSource({ alias }, options)`.
- **Security.** `withoutHiddenFields` refuses a call whose `fields`, in any record it takes (a list, names separated by commas or a sparse fieldset), names a hidden field of the tables its owner owns, whatever the method. Only the seven standard reads refused one: a method `decorateRepository` adds that forwards the caller's `fields` answered the field stripped, as undefined, which a caller used as a value (a token in an email link). A system context, or one it derived, counts in whichever record the call takes, where only the last one counted.
- `withoutHiddenFields` refuses owned tables of which one hides a field and another shows a field of the same name, with a TypeError naming both, when the feature's repository is built: it strips hidden fields by name, so the visible field never reached another feature. Hide it in both, or rename one.
- Runs on json-rest-api 3.0.1 (from 3.0.0), exactly. A handle's `createMany` with `onConflict: { action: "merge" }` inside a transaction that read before another transaction committed the same key no longer fails as forbidden ("the record these conflict keys match cannot be changed by the caller") on MySQL and MariaDB, so two first registrations of one email at once both land; and a merge whose late matched row it left unchanged answers that row instead of empty data. PostgreSQL and SQLite behave as before.
- `expectScoped` compares the other owner's stored rows, every column read through the system context's scoped query, where it compared the records a handle answers. A path that changed only a hidden or `defaultExclude` field of another owner's row (a `patchWhere` under a system context with `returning: "none"`), or a column outside the table resource's schema, passed.
- `@jskit-ai/database-runtime` is a required peer dependency at the same version, where it was a dependency: the application holds one copy of the table runtime, since a nested copy brings its own error classes and transactions.
- `./server` also exports `isSystemContext(context)` and the runtime's defaults, `DEFAULT_REQUEST_ROW_LIMIT` and `DEFAULT_SERVER_PAGE_SIZE`; `./test` re-exports database-runtime's `TestDatabaseMissingError` beside `requireTestDatabase`; `./server/types` holds the types of `runtime.resources`, its handles, call options and system contexts.
- `delete`, `deleteWhere` and `createMany` refuse `lockVersion` and `onlyIf`, and `patchMany` and `patchWhere` refuse `lockVersion`, with a TypeError naming the resource, the method and the key and saying what to do instead (`notes.delete() cannot compare lockVersion, so it refuses rather than write without them. …`). They ignored them, so a delete meant to apply only to an unchanged record deleted it whatever it held. A delete compares in a transaction (`lock()`, compare, delete), `deleteWhere` in its filters, and a many-row patch with `onlyIf` on the lock version field.
- A `patch` with `onlyIf` and no changes compares onlyIf in SQL, on the table as `scopedQuery` gives it, as the UPDATE of a patch with changes does: it compared the record a read answered, with strict equality, so an id given as a number never matched the text the record answers, and a hidden field, which no read answers, never matched at all. It refuses an onlyIf field that is the id or not stored, and a value other than a scalar, a Date or null, as that UPDATE does. A `patch` with `lockVersion` or `onlyIf` locks only the lock version, since onlyIf is compared in SQL.
- `createdAt` and `updatedAt` a caller sets itself (in a system context or one it derived) are cut to the field's `temporalPrecision`, as the handle's own stamps are: a job's `Date#toISOString()`, with milliseconds, was refused (REST_API_VALIDATION) on a table whose timestamps declare `temporalPrecision: 0`. The fraction is cut, never rounded; a value with no fraction, or that is no date-time, is left for validation to judge.
- `./server` exports `passedOn(options)`, what a call hands on (its context and transaction), from `@jskit-ai/resource-core/shared/callOptions`. Code that must load without the table runtime and the database (an assistant on file storage, where `@jskit-ai/resource-runtime` is an optional peer and not installed) imports it from resource-core, a dependency it has.
- **Security.** `withoutHiddenFields` guards every function the repository holds, not only the seven standard reads: whatever a method answers (its records, in arrays, maps and nested plain records, and those of its sub-repositories) leaves without the hidden fields of the tables its owner owns, unless the call's options (its last record argument) carry a system or derived job context. A read an owner added in `decorateRepository`, such as one forwarding the caller's `fields` to its handle's `queryAll`, handed hidden values to any caller. A handle's `scopedQuery` is refused under any name, and `withTransaction` and `lockOrCreate` answer the caller's own work as it is. `withoutHiddenFields(repository, resources)` takes the served resource, or a list of it first and the owner's other tables. A function that answers a Knex value rather than rows (`raw()`, `column()`, or an owner's join source answering a builder) answers it as it is, unawaited, so another feature still builds its scoped query or subquery on it.
- **Security.** `withoutHiddenFields`, the repository a CRUD feature gives other features and its own actions, refuses `scopedQuery()` on a table with hidden fields unless it runs in a system context or one it derived: its builder selects every column, so `(await repository.scopedQuery({}, options)).query.select(repository.column("tokenHash"))` read another feature's hidden values. The owner's own methods, its join sources among them, build on the handle as before.
- `expectFlatQueries` fails when the path sent no statement at any size. That is a test counting on a channel the path does not use, such as no `knex` in a test whose features run on one and that booted no server, which measured 0 at every size and passed.
- A call's settings stay on that call. `withTransaction` hands its work only `{ context, trx }`, and so does a handle to its `afterWrite` hooks, to `lockOrCreate`'s work and to its own nested calls, instead of every option the caller passed: an outer `returning: "none"` made a create inside, or `findOrCreate`, answer nothing, and an outer `missing: "skip"` made a get inside answer null for a missing record. A handle's own write and read still take its `format`. `passedOn(options)`, exported from `./server`, gives the same `{ context, trx }` to code that calls another table.
- The `createdAt` and `updatedAt` a handle stamps are cut to the field's `temporalPrecision` (whole seconds for 0): they always carried milliseconds, so every create on a table whose timestamps declare `temporalPrecision: 0` failed with TYPE_CAST_FAILED.
- A row policy (an owner's or a contribution) is told who the call runs for only as `caller`: json-rest-api's own `system` flag is no longer handed on beside it, so a policy has one way to tell a system context, a job, a user and no one apart. No JSKIT policy read the flag.
- `expectScoped` compares the path's answers: it seeds owner A and runs the path as A, then seeds owner B and runs it as A again, and fails when the second answer differs from the first, as well as when the path changed or removed a row of B's. It used to fail only when the answer held one of B's rows by id with the same fields, so a report that joined, summed or counted B's rows (an answer like "Pat at business B") passed. The path runs twice, so a write answers what repeats. B's rows are read back by id, a thousand per read, and the tables' ids in one statement each, instead of whole tables through `queryAll`, which refused a table past its row limit.
- A handle's plain read answers the hidden fields (`hidden: true`) its `fields` names: `get`, `query` and `queryAll` in their params, and `lock`, `lockMany`, `lockWhere` and `claim` in their options. json-rest-api never selects a hidden field, so the handle reads them in one more statement per 1,000 records, on the table as `scopedQuery` gives it (the caller's ownership and the row policy applied), in the call's transaction, and answers them as json-rest-api reads their type. A hidden field may be an id, string, integer, number or boolean; naming one of any other type refuses the read before it runs. A read without `fields`, and any JSON:API read (`format: "jsonapi"`), still never answers one. Before, an owner read its own bearer token or storage key with a `scopedQuery` report, and a job that had to learn each row's owner across workspaces had to unhide the ownership field.
- `withoutHiddenFields(repository, resource)` (`@jskit-ai/resource-runtime/server`) answers the repository an owner gives other features: the same, except that a read whose `fields` names a hidden field of the resource is refused, with a TypeError naming the method and fields, unless it runs in a system context or one it derived. A resource without hidden fields keeps its repository as it is.
- **Breaking.** A query field's `select` (an `owns` entry's `queryFields`) receives `{ raw, column, filters }` instead of json-rest-api's `{ knex, db, column, context, ... }`. `raw(sql, bindings)` builds one SQL expression from a string and its bindings as an array, and is a value only: it is no promise (its `then` is undefined, so awaiting it answers the expression itself, unrun), and running it as a statement (`catch`, `finally`, `asCallback`, `stream`, `pipe`) throws. `column(field)` names a field's column, and `filters` is the read's filters, frozen. A select could run any statement on the Knex it was handed, with no ownership scope; now it writes the field's value and nothing else: `select({ raw, column }) { return raw("?? - coalesce(??, 0)", [column("receivedWeight"), column("processedWeight")]); }`. A handle's `raw()` refuses the same way bindings that are not an array, or a third argument. jskit/sql-literal holds a destructured `raw(...)` to the rules it holds `handle.raw(...)` to (one literal, bindings for its placeholders, no statement words).
- `lockWhere` and `claim` take `fields` in their options, as `lock` and `lockMany` do (`{ ...txOptions, fields: ["stage"] }`), and read only those, so a belongs-to field left out costs no check that its related record is visible: a claim of a job that links to two tables was a locking read and two checks, and is the locking read alone. Without `fields` they read what `lockMany` reads, so a collection with `hydrateOnView: false` is no longer loaded unless `fields` names it.
- A handle write refuses a condition its options name with no value: `patch` with `lockVersion: undefined` or `onlyIf: undefined`, and `patchMany` or `patchWhere` with `onlyIf: undefined`, throw a TypeError naming the resource, the method and the key (`notes.patch() options.lockVersion is undefined`). They used to run without the condition, so a version read under the wrong field name made a version advance only read. A call without the condition leaves the key out.
- An error a transaction's work throws itself reaches the caller of `withTransaction` (or of a handle call that opened its own transaction) reporting `transactionOutcome: "rolledBack"`, not enumerable, with its status and code unchanged, so `isLostDuplicateInsertRace` and a caller's retry tell a rolled-back duplicate the work turned into its own 409 from one inside a joined transaction. A frozen error is rethrown as it is.
- A handle's `query`, `queryAll` and `aggregate` whose filters give an empty list to a list filter (the id filter, or a filter with `filterOperator: "in"`) answer without a statement what a read matching no row answers: no records (`hasMore: false`), and for `aggregate` no groups, or one row of totals whose counts are 0 and other measures null. The context, page size and filter guards still run first; a JSON:API (`format: "jsonapi"`) query still reads.
- **Security.** `createStandaloneResources` refuses, on the Knex client of a JSKIT server, a table one of the server's features owns, saying which: standalone resources (for a command-line script) built a runtime of their own, with its own table owners and any system scope, so code inside a server could own an app table a second time and read it past its owner. A second Knex client on the same database is not recognised; code inside a server uses its features' handles.
- A job context from `forWorkspace`, `forUser` or `forWorkspaceUser` carries the event scope of its workspace, user or both (`{ kind: "workspace", id }`, `{ kind: "user", id }`, `{ kind: "workspace_user", id, scopeId, userId }`, as a request there does), so an action event it publishes reaches that audience, where it was scoped global.
- **Security.** A context that names no workspace or no user is refused wherever a table owned by it is read, not only on that table's own handle: an `include`, a link's visibility check and a link write into a workspace- or user-owned table now fail with json-rest-api's `REST_API_AUTOFILTER_CONTEXT`, where they read or linked the rows whose owner is NULL. The workspace and user owner resolvers answer nothing (undefined) when the context names no owner; only `workspace_or_shared` keeps its own resolver, which answers null, so a context with no workspace still reads only the shared rows.
- `own()` refuses at startup a cross-table filter (a `searchSchema` or field `search` entry whose `actualField` or `oneOf` names "resource.field") whose target field is not declared `indexed: true`, naming the filter, the target and the fix. json-rest-api refuses that filter only at the first query that uses it. A filter whose target table no feature owns yet is checked when its owner owns it.
- Runs on json-rest-api 3.0.0's release candidate (a17b722). A record written back as it was read keeps a link to a target the writer cannot see: the null it read counts as unchanged, while linking or clearing a visible target applies. A read that includes a link's target no longer checks that link's visibility again (one statement fewer per included type). A system context may group by and count distinct a hidden ownership field, so a job finds its units through its handle; a request is still refused. Stored integer and number values over BIGINT columns read as numbers when exact; ids stay strings, and getter, computed and virtual fields keep their own values.
- A system context's `forWorkspace`, `forUser` and `forWorkspaceUser` take `{ actorId }` last, for work a job does for one person (a request it carries out later). The derived context carries it as `onBehalfOf`, which audit fields read with the kernel's `resolveAuditActorId(context)`, and a row policy sees it as `caller.actorId` beside `kind: "job"`. It is attribution only: it never changes which rows the job reaches, and it signs no one in, so `resolveActorId`, `requireAuth` and an action's `authenticated` permission still see no one. Any other last argument is refused.
- `@jskit-ai/resource-runtime/test` exports `startTestFeatures({ knex, features, requires, inputs, createTables, logger })`: it starts features and providers as an application's server does, without HTTP, on a test resource runtime over the test's Knex, with the kernel's events and actions. The kernel orders them by their requires, each owner gets its handles and system context, every boot runs (so `crud.contracts` is sealed), and it answers `{ capabilities, resources, stop }`, where `capabilities` holds what `requires` names.
- `patch(id, changes, { ...options, onlyIf })` compares a `hidden` field: the UPDATE compares the onlyIf values itself, after the lock that tells a missing record from a changed one, where the handle compared them with the locked record, which no read gives a hidden field, so such a patch never applied unless it also said `missing: "skip"`.
- A row policy (and each contribution) receives `caller`, who the call runs for: `{ kind: "system", reason }` for a system context, `{ kind: "job", reason }` for a context `forWorkspace`, `forUser` or `forWorkspaceUser` derived from one, `{ kind: "user", userId }` for a signed-in request and `{ kind: "anonymous" }` otherwise. A derived job context names no user, so a policy that keyed on the actor treated it as an anonymous request; it now tells them apart by `caller.kind`. `system` is still passed.
- A table whose primary key is a `uuid` or a `string` takes its ids as text without a `normalizeId` on its `owns` entry; json-rest-api's default normalizer takes numeric ids only and answered "Resource document id is invalid". An owner's own `normalizeId` still wins.
- `createMany` with `onConflict: { action: "merge" }` and no `merge` list works on a table that stores `createdAt`: the merge list the handle builds from the rows' fields leaves out the conflict keys, the ownership fields and the lock version, which json-rest-api refused to merge ("onConflict.merge cannot change …"), as well as the id and `createdAt`.
- `aggregate` counts `id` (`{ count: "id" }` or `{ countDistinct: "id" }`) as the count of rows, on a schema that declares no id field too; json-rest-api refused it as an unknown field.
- A handle's included records read as a read of their own resource answers them, at every depth and in an included collection: a belongs-to field carries its id under its own key (`pet.contactId`) and the related record stays nested only when the include names it (`include: "pet.contact"`), where an included record kept json-rest-api's shape (`pet.contact: { id }`, no `contactId`). An included record leaves out a collection it does not include itself, which json-rest-api does not read for it and would answer as empty.
- `lock` and `lockMany` take `fields` in their options (`{ ...txOptions, fields: ["stage"] }`) and read only those, so a belongs-to field left out costs no check that its related record is visible: a lock of a record with two relations was a locking read and two checks, and is the locking read alone. A `patch` with `lockVersion` or `onlyIf` locks only the fields it compares, so its own locking read checks no relation, and `onlyIf` may now compare a field reads hide by default (it never matched before).
- A sparse `fields` names a belongs-to field by its own key (`customerId`) as well as by its relationship (`customer`): the key used to select no relationship and answer `customerId: null` for every row. A sparse read leaves out a belongs-to field it does not name, where it answered `null`.
- A collection relation with `hydrateOnList: false` (lists: `query`, `queryAll`) or `hydrateOnView: false` (`get`, `lock`, `lockMany`) no longer loads its rows on that kind of read unless the read includes it or names it in `fields`, as the CRUD runtime before the redesign did.
- On a table with a lock version, a patch that changes no field still advances the version, and now stamps `updatedAt` as every other update does: `patch(id, {}, { lockVersion })` (which did not stamp before) and an empty `patchMany` row, so many records advance in one UPDATE (`patchMany(ids.map((id) => ({ id })), options)`). A table without a lock version still writes nothing for an empty change.
- **Breaking.** Every handle owns the `id` filter, which takes one id or a list (`filters: { id }`), and registering a table resource that declares its own refuses: a `searchSchema` `id` entry (shared or the owner's) or `search: true` on the `id` field. A declared scalar `id` entry used to replace the handle's, so `filters: { id: ids }` failed on that table. **Upgrading:** delete the resource's `id: { type: "id", actualField: "id" }` search entry and any `search: true` on its `id` field; filters by one id or a list keep working.
- **Breaking (security).** A system context comes only from a declared system scope. `runtime.resources` no longer has `createSystemContext`: `declareSystemScope(featureId, systemScope)` records the scope (one per feature; declaring another throws) and answers the feature's `systemContext(reason)` factory, which the kernel hands a feature's setup, and `systemScopes()` lists them. `createResourceRuntime` and the `./server/resourceHost` subpath are no longer exported, so no code outside the package builds a runtime or a host of its own: code outside a JSKIT server owns its tables with `createStandaloneResources({ knex, feature, owns, systemScope? })`, which answers `{ resources, systemContext? }`, and tests with `createTestResourceRuntime` from `./test`, which now takes `hostHooks` for json-rest-api hooks a test installs. `buildJsonRestQueryParams`, `resolveWorkspaceScopeValue` and `resolveUserScopeValue` are exported from `./server`. `resolveUserScopeValue` throws when a context's `scopeValues.userId` and `visibilityContext.userId` name two users, as the workspace resolver does for two workspaces, instead of the scope value winning.
- A table resource whose schema stores `createdAt` and `updatedAt` as date-times has every handle write stamp them: `create` and `createMany` stamp both, `patch`, `patchMany`, `patchWhere` and an upsert merge stamp `updatedAt` (a merge keeps the stored `createdAt` of a record it updates), and a patch that changes nothing stamps nothing. The stamps replace what the caller sends, so a request can never forge them; only a system context, or a context it derived (an import, a migration, a seed), sets its own, and a timestamp it leaves out is stamped. A call without a context, which server code may make on a public table, is a request's: server code cannot pass a forged body through, and a feature that writes its own timestamps declares a `systemScope` and writes in its system context. Only the CRUD service stamped them before, so server code that wrote through a handle left them unchanged.
- Handles gain `lockOrCreate(row, options, work)`: on a table with no owners it locks the record with `row.id`, creating it from `row` first when it is missing (an insert that ignores a clash on the id), and runs `work(record, txOptions)` in that transaction, so work that fails leaves no record behind. In the caller's transaction it runs there once; on its own it opens a transaction that runs work once, and when two first uses of one id collide on the insert (a deadlock, or a duplicate key) before work starts, the loser runs again, up to four runs in all.
- **Breaking: the package is now `@jskit-ai/resource-runtime`** (was `@jskit-ai/json-rest-api-core`), on json-rest-api 3.0.0. Its provider is `ResourceRuntimeProvider`, which provides `runtime.resources`; the host it builds is `createResourceHost` (was `createJsonRestApiHost`), at `./server/resourceHost` (was `./server/jsonRestApiHost`). The `runtime.json-rest-api` capability and the host helpers `addResourceIfMissing`, `createJsonRestResourceScopeOptions`, `queryAllJsonRestCollectionRows`, `queryAllJsonRestCollectionDocument` and `extractJsonRestCollectionRows` are removed: a feature owns its tables with `defineFeature({ owns })` and reads every matching row with its handle's `queryAll`.
- **`runtime.resources`.** The kernel calls `own(featureId, owns)` for a feature with `owns`: it registers each table resource (or `{ resource, rowPolicy, hooks: { afterWrite }, acceptsContributions, normalizeId, queryFields, searchSchema }`) under its name, throws `DuplicateOwnerError` when another feature owns the table or the name, and answers one handle per resource. `createSystemContext({ feature, systemScope, reason })` answers json-rest-api's system context, with `forWorkspace(id)` and `forUser(id)` for work scoped to one workspace or user.
- **Handles.** Every method takes `options = { context, trx }` last and refuses an owned resource's call without a context (`MissingScopeError`). Reads: `query(params)` answers `{ records, page: { size, hasMore, next } }` and requires `page.size` (`UnpagedQueryError`) no larger than the resource's page limit (`PageSizeError`), with `page.after` (the previous page's `next`) for scrolling or `page.number` (from 1) for a numbered page, each one statement with no count; `queryAll` reads in 1,000-row pages and, in a request context, throws `RowLimitError` past 10,000 rows (a 400 coded `RESOURCE_ROW_LIMIT`, with the message code `resource.rowLimit` for the user's language) (system, workspace and user job contexts have no limit); `get(id, params, options)` answers a record; `aggregate` answers rows. Writes: `create`, `patch` (answers the record; `lockVersion` throws `StaleRecordError`, 409 `crud.document.lockVersionConflict`; `onlyIf` patches only matching rows and answers null otherwise) and `delete` (answers the id), and the many-row `createMany`, `patchMany`, `patchWhere` and `deleteWhere`, one statement per chunk. One missing-row rule: `get`, `patch`, `delete` and `lock` throw json-rest-api's not-found error (404) for a missing or hidden row, and answer null with `missing: "skip"`, which never fails the caller's transaction. Every filter takes `id`, one id or a list, so `patchWhere({ id: ids }, changes)` and `deleteWhere({ id: ids })` cover a list of ids. An upsert's rows carry no id, and `patchWhere` and `deleteWhere` with empty filters need `all: true`. Locks: `lock`, `lockMany`, `lockWhere`, `claim({ filters, sort, take }, options)`. Escape hatch: `scopedQuery` answers `{ query }`, a read-only builder with ownership and the row policy applied, with `column` and `raw`. Reads take `(params, options)` and writes `(data, options)`; settings ride in options, as `{ ...options, lockVersion }`. `withTransaction(options, work)` runs work in the caller's transaction or one it opens and retries a deadlock victim unless `{ ...options, retry: false }`; `{ ...options, outermost: true }` refuses a call inside a transaction. When work throws, the caller gets its own error; a failed write inside it or a failed commit arrives as json-rest-api's `RestApiWriteError` with the transaction's outcome. `findOrCreate({ id, ...attributes }, options)` reads the record with that id or creates it, and answers the winner's record when a concurrent creation wins outside a transaction. An id another scope's row holds answers a missing record, as `get` of it does, never `null` or that row, so it tells the caller no more than any id it cannot see. `afterWrite` hooks run once per write in its transaction and scope.
- A system context also derives `forWorkspaceUser(workspaceId, userId)`: one user's context inside one workspace, so a `workspace_user` table reads that user's rows in that workspace, a `workspace` table the workspace's and a `user` table the user's. Both ids are required.
- **Row policies** receive `ownTable(name)`, a SELECT-only builder over the owner's own tables, and a resource whose owner says `acceptsContributions` takes other features' `contributeRowPolicy(name, policy)`: each contribution is ANDed with the owner's policy inside its own group, so it only narrows.
