# Changelog

## Unreleased

- `retryLostInsertRace(options, run)` (from `./shared`) runs a transaction once more when its insert lost a race for a unique key: `run`, usually `() => repository.withTransaction(options, work)`, failed with a duplicate whose transaction rolled back in full, outside a caller's transaction (`isLostDuplicateInsertRace`). The database reports the duplicate only once the winner has committed, so the second run's lookup by the key finds the winner's row; a second duplicate is final, and inside a caller's transaction (`options.trx`) the error reaches the caller without a rerun. Apps wrote this retry by hand around each idempotent write.
- The migration configuration lists the application's `migrations/constraints/` only when the directory exists, as it already did for a package's: an application without one failed `db:migrate` and `jskit test --databases` with ENOENT (scandir `migrations/constraints`).
- `retryDeadlocks` (and so `withTransaction` and every handle write outside a transaction) also runs again a transaction that MariaDB failed as "Record has changed since last read" (errno 1020, `ER_CHECKREAD`): with `innodb_snapshot_isolation` on, the second of two writers whose filters matched one row fails so when it locks the row the first changed. json-rest-api has rolled the transaction back, so the new run reads a fresh snapshot, and a `patchWhere` or `deleteWhere` then leaves out the row that no longer matches. `isDeadlockError` recognises it.
- **Breaking.** `runtime.database` is `{ driver, knex }`: its `transactionManager`, with `inTransaction(work, { trx })`, and the `RuntimeTransactionManager` type are removed, so a transaction has one way in, the table handle's `withTransaction(options, work)`, which joins the caller's transaction and retries a deadlocked outermost one. Nothing in JSKIT called it. Code that opened a transaction with it opens it on a table's handle (or its owner's API) instead.
- A PostgreSQL session runs in UTC whatever the server's default time zone, as a MySQL connection does with `timezone: "Z"`: the runtime's Knex and the migration configuration (`createKnexMigrationConfig`) set `TimeZone` to UTC in the pool's `afterCreate`, and the test databases' own connections keep it. PostgreSQL reads a date-time written without an offset, as the `datetime-utc` storage writes it, in the session's zone, so on a server set to another zone a `timestamptz` value moved by that zone's offset.
- The test databases' `tableNames()` and the migration ledger read accept every name Knex gives PostgreSQL's client (`pg`, `postgres`, `postgresql`); `postgres` used to be read as MySQL.
- `retryDeadlocks` runs a transaction again only when the database chose it as a deadlock victim, never after a lock wait timed out (MySQL's 1205 and PostgreSQL's `55P03`): MySQL rolls back only the timed-out statement, so a rerun could repeat the transaction's earlier work. Behaviour is unchanged; tests now pin it.
